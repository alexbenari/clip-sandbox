## Purpose

Clip Sandbox is a local Electron desktop app for reviewing video clips from one selected folder at a time. The durable model is a `Pipeline`: a folder-backed container of all clips plus zero or more saved collections. The user can browse the full pipeline, switch to a saved collection, reorder clips, save or save-as-new, add to another collection, move clips to the Recycle Bin, zoom a clip, refine a zoomed clip's start and end and loop it forward then backward (Loopify) in Zoom edit mode, and enter fullscreen review mode.

The renderer is still framework-free. The main architectural change from the OO/TypeScript refactor is that authored renderer code now lives in `src/**/*.ts`, the Electron shell remains pragmatic CommonJS, the adapter layer under `src/adapters/` is now class-backed, and `index.html` loads emitted runtime JavaScript from `build/src/...`.

## Stable Concepts

1. `Clip` in [`src/domain/clip.ts`](../../src/domain/clip.ts): canonical runtime clip object with generated id, its [`ClipSource`](../../src/domain/clip-source.ts) (an immutable value: file name, the media address the grid and Zoom play, and the desktop path when there is one, built only through `ClipSource.create`), duration, intrinsic video dimensions, metadata failure state, and the [`SourceMovie`](../../src/domain/source-movie.ts) its file's source-info tag names (`null` until read or when there is none). `Clip.replaceFile(source)` puts a new file under the same clip (Replace in Zoom edit mode) and clears what was learned from the old one. The domain uses no DOM type; several of its specs pin the Node test environment to prove it.
2. `ClipSequence` in [`src/domain/clip-sequence.ts`](../../src/domain/clip-sequence.ts): mutable runtime ordered clip list used by the grid, selection, reorder, and transient view state.
3. `Collection` in [`src/domain/collection.ts`](../../src/domain/collection.ts): durable ordered subset of pipeline clip names, optionally backed by a `.txt` file, with collection-specific append/remove/materialization behavior.
4. `Pipeline` in [`src/domain/pipeline.ts`](../../src/domain/pipeline.ts): folder-backed container of one `ClipSource` per available video plus zero or more saved `Collection` objects. It owns one canonical runtime `Clip` per active-session video file, explicit `materializePipeline(...)` / `materializeCollection(...)` flows, and in-memory collection/video mutation rules such as `addClipsToCollection(...)`, `removeVideos(...)` and `replaceVideoFile(...)` (which keeps the clip's id and renames it in every collection that lists it).
5. `PipelineWorkingCopy` in [`src/app/pipeline-working-copy.ts`](../../src/app/pipeline-working-copy.ts): active loaded-pipeline working state. It owns generated clip ids, the selected pipeline/collection sequence, derived dirty-state comparison (never a cached flag), active clip resolution, reorder/remove mutation, created-clip insertion and clip file replacement while keeping the durable `Pipeline` focused on folder contents and saved collections.
6. `AppSessionState` in [`src/app/app-session-state.ts`](../../src/app/app-session-state.ts): class-backed app-shell state holding the open folder's `FolderAccess`. The pending selection action waiting on the unsaved-changes prompt belongs to `FolderSelectionWorkflow`. It does not own loaded pipeline selection state.
7. `CollectionFullScreenWorkflow` in [`src/app/collection-full-screen-workflow.ts`](../../src/app/collection-full-screen-workflow.ts): Collection-only full screen coordinator for slot input, title hiding and rotation scheduling. It passes slot values and rotation requests to the grid; it receives no card/video handles. [`FullscreenAdapter`](../../src/adapters/browser/fullscreen-adapter.ts) distinguishes the document-root Collection element from the GIF player's element while retaining an app-wide any-full-screen check.
8. [`FolderAccess`](../../src/app/folder-access.ts) (held by `AppSessionState` as `currentFolderAccess`, `null` when no folder is open): access to the opened desktop folder, backed by its absolute path. Only [`ElectronFolderService`](../../src/adapters/electron/electron-folder-service.ts) creates one, checking the path where it arrives from the desktop API, so callers need only a null check. [`FolderAccessRegistry`](../../electron/folder-access-registry.cjs) records picker-selected paths and explicitly opened catalog pipelines as per-window folder grants; listing or expanding the catalog grants only opaque read access to its entries. Only a granted folder can be written, appended to, have files moved to the Recycle Bin, or be re-enumerated through Electron IPC.
9. `clipSandboxDesktop` in [`electron/preload.cjs`](../../electron/preload.cjs): preload-exposed desktop API used by the renderer-facing Electron services.
10. `ZoomEditComposition` in [`src/domain/zoom-edit-composition.ts`](../../src/domain/zoom-edit-composition.ts): combines staged edits. Each edit is a stateless class implementing `IZoomEdit`, shared by both processes: `declaration()` gives its name, order (cut, then a later speed edit, then loop), whether it keeps sound and plays backward, whether it needs the source movie (Refine yes, Loopify no), the source info it allows, and its file-name suffix; `wordsFrom(wording)` takes its label and adjective from `IZoomEditWording`, which has one method per edit (`refine()`, `loopify()`), so a new edit does not compile until [`ZoomEditModeText`](../../src/app/zoom-edit-mode-text.ts) words it and the domain holds no user text; `refusal(facts)` refuses a staged range (`{ changesRange, frameCount }`): Refine one that does not change the clip, Loopify one of fewer than two frames. Edits cross the process boundary by name, so one name-to-edit table remains (`names()`). The composition answers how they combine: sound dropped if any edit drops it, the source movie needed if any edit needs it, weakest source info wins, one suffix per edit in order (such as `-refined-looped`), the edits' words in order (`wordsFrom`; `wordsOf` for one edit, as the Zoom edit menu needs) and the first refusal in order. The renderer's staged edits, [`IStagedEdit`](../../src/app/staged-edit.ts) (`StagedRefine`, `StagedLoopify`), are the user's unsaved choices in one session: each says whether it is staged and what leaving would discard. The main process loads the same compiled module (`loadEditComposition` in `main.cjs`) for saving and previews.
11. `StagedEditResolver` in [`electron/staged-edit-resolver.cjs`](../../electron/staged-edit-resolver.cjs): checks a renderer's staged edits for both saving and previews (folder grant, clip name, the review session showing the source, range limits, and the `edits` list: known names, no repeats, not empty) and answers the cut (`ClipCut` or `WindowCut`, which knows whether the range differs from the whole clip) with its `ZoomEditComposition`, refusing a range that composition refuses. Paths never come from the renderer.
12. [`ActivityLogger`](../../src/app/activity-logger.ts) owns the session activity contract, progress/success/error state, retained history, and change subscriptions. [`ActivityIndicatorControl`](../../src/ui/activity-indicator-control.ts) subscribes and renders the global status surface, detailed errors, and local interactions.
13. The loop preview: [`ZoomEditLoopPreview`](../../src/app/zoom-edit-loop-preview.ts) (renderer, owned by the edit session) keeps one rendered preview for the staged edits it was made from; [`ZoomEditPreviews`](../../electron/zoom-edit-previews.cjs) (main process) renders it with FFmpeg into `<userData>/zoom-edit-previews/`, one preview per app window, cleared at startup, on release and at quit.
14. `frame-review native toolchain` in [`native/frame-review/`](../../native/frame-review/) and [`tools/frame-review/`](../../tools/frame-review/): explicit Windows x64 build-time ownership for the selected LibVLC playback service, BestSource exact-frame service, bounded binary protocol, diagnostic helpers, and one pinned x264-enabled FFmpeg/FFprobe distribution. Normal build/startup never bootstraps or compiles it.
15. `FrameReviewHost` in [`src/frame-review/host/frame-review-host.ts`](../../src/frame-review/host/frame-review-host.ts): trusted per-window owner of opaque source handles and review sessions. `ReviewSession` coordinates provisional LibVLC playback, asynchronous prepared-review activation, exact BestSource access, source-generation invalidation, bounded scrub/held-step workloads, and idempotent disposal. Playback commands and proxy activation are serialized so a Play after Pause cannot be overwritten by a concurrent proxy open. It owns live-clock relative playback jumps and elapsed-time lookup of exact scrub frames. Main-process callers also use it without a renderer: `exactFrameReader` (frame count and identities of an exact-ready session, after checking the session shows that source), `findFrameByCheckValue` (the first frame in a given order whose check value matches), `cachedFrameTimesUs` (frame times from a prepared movie's cached index, `null` rather than ever building one, and `null` for a normalized source) and `forgetPreparedReview` (removes a source's prepared-review cache entries). A file's native measurements (fingerprint, stream and dimensions) come from [`SourceMeasurementCache`](../../src/frame-review/host/source-measurement-cache.ts), one per cache file shared by every host, so an unchanged file (same path, size and modification time) is measured once across app sessions; see [Native Frame-Review Runtime Boundary](#native-frame-review-runtime-boundary). The renderer reaches it only through [`electron/frame-review-ipc.cjs`](../../electron/frame-review-ipc.cjs) and [`ElectronFrameReviewService`](../../src/adapters/electron/electron-frame-review-service.ts); source, index, proxy, and cache paths never appear in that renderer service contract.
16. `FrameReviewPlayerControl` in [`src/ui/frame-review-player-control.ts`](../../src/ui/frame-review-player-control.ts): the single renderer-owned movie viewport, transport, readiness presentation, progress bar, and GIF movie full screen owner shared by GIF Extraction, Refine Gif and Zoom edit mode. Where it is mounted decides its look: `mountInGifScreen(host, emptyMessage)` gives the full player, `mountInZoomEdit(host)` the picture only (the `zoom-edit-look` class hides readiness, progress row, transport, empty and busy states); muting is not part of the look but of the movie opened (the frame-review open request's `muted`, which `ReviewSession` passes to the playback engine). The player element alone enters full screen after exact readiness; the existing seek row appears temporarily, and `fullscreenchange` reconciles focus and presentation without a shell screen change. Movie playback runs at the native player's default 1× speed; progress seeking and exact-frame scrubbing remain separate commands. It owns the transient jump duration, last manual scrub direction, bounded pending jump time, and interruption order; [`GifWorkflowKeyboard`](../../src/ui/gif-workflow-keyboard.ts) maps physical top-row digit shortcuts to the same command as the Jump button and routes `F`/`Escape` for movie full screen. Attaching a new review session resets the timeline, displayed time, and scrub direction before new frames arrive; if the player was full screen, new-frame painting waits for normal presentation. It renders capture identity from the newest displayed frame synchronously and never owns or disposes the leased review session.
17. The GIF session: [`GifExtractionSession`](../../src/app/gif-extraction-session.ts) serves GIF Extraction and Refine Gif (opens a movie by picker, marks and locks ranges). It builds its parts and assembles the one snapshot both GIF screens and the Clips panel read:
   - [`GifSessionStatus`](../../src/app/gif-session-status.ts): the status line and preview revision; the single trigger for publishing;
   - [`CurrentMovie`](../../src/app/current-movie.ts): choosing, opening and following the movie under review, its source generation, preparation and readiness reporting; it reports `exactCaptureReady` and `reviewEnded` as events, and the session drives a change of movie;
   - [`CaptureQueue`](../../src/app/capture-queue.ts): the draft and locked ranges, their thumbnails, the saved-frame checks (run by locking and refining themselves), removal and restoring saved captures; it saves through [`SavedCaptureStorage` or `UnsavedCaptureStorage`](../../src/app/capture-storage.ts), which the composition root chooses;
   - [`RangeExtraction`](../../src/app/range-extraction.ts): extraction runs and their Activity reporting;
   - [`RangeRefinement`](../../src/app/range-refinement.ts): starting, abandoning and committing a refinement.
   
   No session has a mode. [`SavedCaptureQueuePersistence`](../../src/app/saved-capture-queue-persistence.ts) owns each source generation's durable queue binding and stale-range marks.
18. `ClipExtractionWorkflow` in [`src/app/clip-extraction-workflow.ts`](../../src/app/clip-extraction-workflow.ts): exact-only single/batch orchestration owner. It preserves per-range outcomes, continues after individual failures, cancels active work, and retries a failed collection publication without re-encoding completed media.
19. `ApplicationShutdownCoordinator` in [`src/app/application-shutdown-coordinator.ts`](../../src/app/application-shutdown-coordinator.ts): idempotent renderer teardown owner. It stops app keyboard and screen actions synchronously, begins workflow disposal, and disposes the controls, including their own input and resize listeners, only after that disposal settles.
20. `AppSettings` in [`src/app/app-settings.ts`](../../src/app/app-settings.ts) and [`AppSettingsService`](../../src/app/app-settings-service.ts): persisted renderer preferences, including `startupScreenId`, its default/fallback (`gif-extraction`), and committed immutable settings state. The service owns load/save; it does not own the active screen.
21. Zoom and Zoom edit mode are separate concepts. Zoom ([`ZoomWorkflow`](../../src/app/zoom-workflow.ts), [`ZoomOverlayControl`](../../src/ui/zoom-overlay-control.ts)) shows one clip and moves through the collection. Zoom edit mode ([`ZoomEditModeWorkflow`](../../src/app/zoom-edit-mode-workflow.ts), [`ZoomEditModeSession`](../../src/app/zoom-edit-mode-session.ts)) is entered from a zoomed clip, owns that clip's staged edits, keys and hint line, and returns the clip to Zoom when it ends. Its edits are Refine (start and end) and Loopify (forward then backward), staged together and saved once; a later edit is one domain edit class in `ZoomEditComposition`, one staged-edit class beside `StagedRefine` and `StagedLoopify`, its key and its `IZoomEditWording` method, without changing Zoom. [`ActiveZoomEdit`](../../src/app/active-zoom-edit.ts) is the one answer to "is the mode active?". See [Zoom Edit Mode](#zoom-edit-mode).
22. `SourceInfo` in [`electron/clip-provenance/source-info.cjs`](../../electron/clip-provenance/source-info.cjs): the main-process owner of a clip's source-info record (its movie, frame range with optional times, and one to four reference frames; or, for a looped clip, the movie alone). A `SourceInfo` names only the movie; a [`RangedSourceInfo`](../../electron/clip-provenance/source-info.cjs) adds the range and reference frames, and `ranged()` answers it or `null`. Only the main process builds records; the renderer's `Clip` keeps only its `SourceMovie` name. See [Source Info](#source-info).

The important split remains durable selection state vs runtime working copy:

1. runtime UI works with `Clip` and `ClipSequence`,
2. active loaded-folder selection state works through `PipelineWorkingCopy`,
3. durable selection and persistence work with `Pipeline`, `Collection`, and explicit pipeline-mode vs active-collection branching,
4. `Collection` remains filename-based durably, while materialized collection sequences reference canonical `Clip` instances from the active `Pipeline`.

## Architecture Axioms

These are normative defaults for future work. Do not violate them without a concrete reason and user approval. UI design follows [`ui-coding-quality.md`](../../ui-coding-quality.md); axioms 2, 3, 7 and 11 record how this repository applies it. Only the composition root (`app-controller.ts`) imports from `src/ui/`; types both layers use, such as [`IShortcutDescriptor`](../../src/app/shortcut-descriptor.ts) and [`IFrameReviewDisplayedCapture`](../../src/app/frame-review-displayed-capture.ts), live in `src/app/`.

1. Keep the renderer framework-free unless a larger architecture decision is approved.
2. Keep [`AppController`](../../src/app/app-controller.ts) as the composition root only: it constructs services, controls, screens and workflow classes, connects them, and starts the application. User flows live in workflow classes under [`src/app/`](../../src/app/) (`*-workflow.ts`); do not put flow logic, domain rules or reusable UI internals in `AppController`.
3. Controls report user intent as typed events (`EventSource` in [`src/app/event-source.ts`](../../src/app/event-source.ts)) that workflows subscribe to; workflows depend on narrow consumer-declared `I…` interfaces and never import from `src/ui/`. A reply to a single request, such as a dialog's submit result or a menu item callback, stays a call argument. Questions other parts ask ("may this screen be left?", "is this name new?") are answered by standalone query components, not workflows. There is no startup check that every event has a subscriber; an unhandled event shows up as a control that does nothing, which the app-level and end-to-end tests are expected to catch.
4. Keep durable pipeline and collection state in domain models plus explicit active-collection selection state, not in DOM order or DOM-selected state.
5. Prefer explicit pipeline-vs-collection flows when their semantics differ materially. Do not introduce shared protocol layers or generic source ids unless they are buying real simplification.
6. Keep Electron main/preload and local filesystem behavior behind adapters or services. Do not leak raw Electron or Node APIs broadly into renderer code.
7. Keep reusable UI behavior in focused controls (`…Control`) and screens under [`src/ui/`](../../src/ui/); `AppController` only builds and connects them.
8. Default production TypeScript behavior to explicit class ownership, including deterministic calculations and text formatting. Treat every module-level function as a design smell that requires an ownership decision; document any intentional exception.
9. Treat [`docs/documentation/object-oriented-exception-register.md`](../../docs/documentation/object-oriented-exception-register.md) as the reviewable record of intentionally non-OO holdouts.
10. Treat `docs/agent-docs/` as the canonical agent-facing architecture knowledge base. Historical specs and plans are not canonical onboarding material.
11. A UI control owns binding and unbinding events originating from its own elements. [`ApplicationEventController`](../../src/app/application-event-controller.ts) is limited to application-wide document/window events. A control that closes or repositions on interaction outside itself (the order menu, context menu and utility panel) may listen on its own element's document and window, and removes those listeners in `destroy()`. A control also finds or creates its own parts and owns its display text: `AppController` passes the document or a root plus behavior (validators, `AppText`, callbacks), never a control's inner elements, attributes or labels. Controls built from the page expose a factory for this, such as `fromDocument`, `forClipMenu`, `DiscardRefinementDialogControl.forZoomEdit`, `RefineGifScreen.forGifExtraction` or `ApplicationShellControl.sidePanelsIn`, using [`DocumentElements`](../../src/ui/document-elements.ts) for required and optional lookups.
12. Inject shared service-like objects such as [`AppText`](../../src/app/app-text.ts) rather than importing static namespaces or free formatting functions.
13. Prefix authored TypeScript interface names with `I`; classes and type aliases retain responsibility-based names without a type-kind prefix.

## Core Runtime Flows

### Native Frame-Review Runtime Boundary

The production-owned native sources are the selected software-only implementation carried from the exact-frame spike: LibVLC owns clocked playback/audio, while BestSource owns indexed canonical frame identity and exact access. The versioned `FVSP` protocol rejects unsupported versions and bounded-length violations before payload allocation. The x264-enabled FFmpeg 9 build supplies `ffmpeg.exe`, `ffprobe.exe`, native libraries, current AAC handling, and `libx264rgb` from one vcpkg dependency graph; QSV, oneVPL, CUDA/NVENC, AMF, and nonfree features are excluded. [`NativeProductLocator`](../../electron/native-product-locator.cjs) is the single development/packaged-layout resolver for frame review, GIF Extraction, Zoom edit mode (movie windows, frame-rate probe, saved clips, loop previews); it also supplies the staged runtime-library environment required by FFmpeg and FFprobe. No legacy `@ffmpeg-installer/ffmpeg` fallback remains.

Run `npm run frame-review:bootstrap`, `npm run frame-review:build`, and `npm run frame-review:test` explicitly. Bootstrap verifies pins and reuses valid dependencies; a clean BestSource bootstrap explicitly fetches pinned Ninja through vcpkg before locating its executable, since dependency installation alone need not populate that tool. CMake owns incremental helper/test targets. `npm run build` and `npm start` do not install dependencies or compile native tools. When the production binaries are already present, Electron composes a `FrameReviewHost` for each window and registers the narrow preload API. The native products are required: missing ones stop startup before any window opens, by design. `createFrameReviewRuntime` in `main.cjs` asks `NativeProductLocator` for FFmpeg and FFprobe while building the runtime, and the locator throws `missing-binary`.

Movie opening has three progressive capabilities. Dedicated frame-review movie selection registers the original source with the window's `FrameReviewHost` and returns an opaque handle; ordinary pipeline folder entries and `ClipSource` values do not retain that session capability. LibVLC opens the selected original source first for provisional playback with audio. `ReviewPreparationService` then inspects the source and validates a content- and tool-version-bound cache identity. On a cold miss it conditionally normalizes timestamps and creates/publishes the software GOP1 review proxy first; `ReviewSession` switches LibVLC to that proxy as soon as it is usable, so timestamp scrubbing no longer waits for exact-frame work. It then builds the canonical BestSource index, indexes the proxy, validates the ordinal frame map, and publishes the complete prepared review. Exact capture remains disabled until that final prepared review is activated. Indexing emits real native progress when the gate supplies totals; other phases are deliberately indeterminate. After exact readiness, frame-scrub delivery carries canonical identity and pixels together; capture during clocked playback remains a timestamp/inexact point. Only progress-bar drags (`dragToFrame`) wait out `ScrubRequestScheduler`'s debounce; a jump to a frame (`goToFrame`, behind `FrameReviewPlayerControl.enterExactScrubAtFrame`, which Zoom edit steps, GIF endpoint jumps and Refine use) is answered at once and drops a waiting drag. A frame that answers a request reaches the renderer only as that answer; held-step frames from the host's `AdjacentStepScheduler` arrive as `display-frame` events.

`PlaybackProxyCache` owns early proxy publication and one process-wide writer per identity; its immutable proxy and optional normalized source live under `<app-folder>/playback-proxy-cache`. `ExactReviewProxyCache` retains atomic publication for the same proxy together with its exact-review set: canonical indexes live under `<app-folder>/frame-index-cache`, while proxy indexes, frame maps, hard-linked proxy/normalized media, and manifests live under `<app-folder>/exact-review-proxy-cache`. Each requesting session is an independent consumer: cancelling one consumer does not cancel a writer still needed by another, while abandoning the final consumer aborts the writer and removes its partial workspace. The application folder is the project directory in development (the Electron profile folder when `CLIP_SANDBOX_E2E=1`, so each end-to-end test starts with empty caches and deletes them with its profile) and the installed executable's containing directory in a packaged build, never an `app.asar` path. Valid full-review hits skip both builders and preserve mtimes across session and process restarts. Temporary partial entries are ignored and cleaned, stale or incomplete entries rebuild, and ordinary session/app shutdown never deletes validated cache assets. Zoom edit mode's movie windows live beside them under `<app-folder>/movie-window-cache` (see [Zoom Edit Mode](#zoom-edit-mode)); evicting a window also removes its prepared-review entries, through a maintenance `FrameReviewHost` that the main process's frame-review runtime owns for cache upkeep and that no app window owns. Entries still being written are never removed. `SourceMeasurementCache` keeps the source inspection's native measurements in `<app-folder>/source-measurement-cache/measurements.json` (at most 64 files, keyed by a hash of the path, never the path, plus size and modification time); it forgets them all when `SourceInspector.toolsVersion` (the size and modification time of the measuring tools) changes, and a host's disposal waits for its writes.

An optional `loop-timeline-v1.json` sidecar beside each prepared proxy manifest stores indexed proxy PTS by ordinal for exact capture preview. [`ProxyFrameTimelineCache`](../../src/frame-review/host/proxy-frame-timeline-cache.ts) validates or regenerates it from the finished proxy index; failure leaves ordinary proxy playback and exact scrub available. [`ReviewSession`](../../src/frame-review/host/review-session.ts) owns the A–B lifetime, ordinal-to-player-time lookup, Space handoff, and reset recovery; the shared [`FrameReviewPlayerControl`](../../src/ui/frame-review-player-control.ts) displays the resulting playback and exact frames. The GIF screens expose A/S exact jumps, Z loop preview, Space pause/resume, and X lock/commit for the active exact draft, selected locked range, or staged Refine pair. A–B picture-boundary misses remain provisionally accepted pending the user's real-clip review; the pinned proxy profile uses zero-origin indexed PTS converted through its rational timebase; the host rejects unsupported nonzero origins. The native service interpolates LibVLC timer points between callbacks, including across loop seeks, for the Space handoff. CFR, VFR, and actual timestamp-normalized coded fixtures exercised this mapping, while final full-suite and user real-clip checks remain in the plan. See the [execution plan](../plans/capture-preview-and-shortcuts-exec-plan.md).

### Application Shell and Screen Ownership

`index.html` defines the global app bar, central command host and main screen host. [`ApplicationShellControl`](../../src/ui/application-shell-control.ts) owns a nonempty set of [`IAppScreen`](../../src/ui/app-screen.ts) registrations, the persistent workspace selector, active content/commands and delegated initial focus. Screen roots stay mounted but inactive roots are hidden/inert; inactive commands are detached. Activation is synchronous, so there are no queued stale completion callbacks. The selector is hidden for a single registration and lives in the global app bar, not in the movie/media workspace. The shell may receive an explicit initial screen id, but it has no screen-id branches or Electron/filesystem dependencies. Before another screen becomes active it asks each of its leave policies ([`RefineScreenLeavePolicy`](../../src/app/refine-screen-leave-policy.ts), [`ZoomEditModeLeavePolicy`](../../src/app/zoom-edit-mode-leave-policy.ts)); a refusal is reported as `screenChangeRefused`, and the workflow that owns the held state asks the user and completes the change.

Production registers [`CollectionScreen`](../../src/ui/collection-screen.ts), [`GifExtractionScreen`](../../src/ui/gif-extraction-screen.ts), contextual [`RefineGifScreen`](../../src/ui/refine-gif-screen.ts), and [`SettingsScreen`](../../src/ui/settings-screen.ts). Fixed screens receive persistent selector entries; a contextual screen receives a temporary truthful entry only while active. Collection adapts the existing Collection DOM, owns initial focus and supplies the grid's allocated content height. `MainToolbarControl` remains the Collection command-state renderer; its name and stable element ids are retained. Existing Activity and the prominent Workspace selector live in the global bar, while movie controls, zoom/context overlays and screen-specific commands remain in their own workspace areas. Settings has no command bar and exposes the persisted Startup workspace preference. The Pipelines catalog uses a persistent fallback host inside the shell panel mount, so screen activation preserves its tree and disclosure state. The shell delivers document key presses to the active screen's `onKeyDown` hook. `CollectionScreen` reports them as `keyPressed`, which `AppKeyDownHandler` handles (Collection shortcuts first, then Collection full-screen keys, but never keys typed into an open dialog or an editable field, and nothing while a global utility is open). While Zoom edit mode is active every key goes to [`ZoomEditModeKeyboard`](../../src/ui/zoom-edit-mode-keyboard.ts) instead, unless a dialog (including the save and discard dialogs) or an editable field has it; plain keys (no Ctrl, Alt or Meta) the mode does not use do nothing (their default action is prevented, so Tab keeps the focus in Zoom and Enter presses no control behind it). Key releases and window blur do not pass through the shell: `AppController` gives `ApplicationEventController` callbacks that hand them to both `GifWorkflowKeyboard` and `ZoomEditModeKeyboard`, which end held steps. Keys pressed on a focused clip card (arrows, Space, Alt+Arrow, Shift+F10, Menu) reach the grid only through that handler's `grid.handleCardKey`, so its guards also keep them out of Zoom and Collection full screen; Enter/Z open the focused or selected clip and Ctrl+S calls `CollectionSaveWorkflow.saveActive`; the GIF screens pass them to their shared keyboard handler, [`GifWorkflowKeyboard`](../../src/ui/gif-workflow-keyboard.ts) is activated and released by the two GIF screen lifecycles.

[`AppSettingsService`](../../src/app/app-settings-service.ts) owns the committed immutable [`IAppSettings`](../../src/app/app-settings.ts) value: an optional Pipelines root, the default audio preference for new single-clip playback (off initially), and the persisted `startupScreenId` preference (GIF Extraction by default); `whenLoaded()` settles after its first load attempt, and `FolderSelectionWorkflow` waits on it before loading a folder. [`SettingsScreen`](../../src/ui/settings-screen.ts) only shows the values and busy state and reports `folderChooseRequested` and `preferenceChangeRequested`; [`SettingsWorkflow`](../../src/app/settings-workflow.ts) loads, saves, chooses the root, reports to Activity, reloads the Pipelines catalog after load or a root change, and opens the saved startup screen unless the user has already moved. The [`Electron adapter`](../../src/adapters/electron/electron-app-settings-service.ts) validates unknown IPC responses and the domain parser owns valid startup-workspace membership. [`AppSettingsStore`](../../electron/app-settings-store.cjs) reads and atomically writes versionless known fields in `app-settings.json` beneath Electron userData. It ignores unrecognized persisted fields and returns their names as data (`ignoredFields`); `SettingsWorkflow` words them and records them as an Activity note (`ActivityReporter.information`), not an error; invalid or unreadable known settings fall back to defaults and are reported as an error. Failed writes preserve the committed value. Native folder cancellation saves nothing. The shell is constructed passive; `start()` performs its first activation after every workflow has subscribed to its `screenChanged` event, so no event fires before wiring is complete; `ApplicationShellControl` owns the active screen after that handoff, not the persisted preference. After settings load, [`PipelineCatalogRuntime`](../../electron/pipeline-catalog-runtime.cjs) reads only immediate child folders of the configured root, keeps folders containing at least one recognized top-level video, and returns opaque per-window catalog ids and names; `extraction-tmp` sorts first and the remaining names sort naturally. [`PipelineCatalogControl`](../../src/ui/pipeline-catalog-control.ts) owns the side-panel disclosure tree: expanding a pipeline lazily reveals distinct Collections and Clips groups, and expanding a collection reveals its listed clip names. Load is a separate action that obtains the opened folder's `FolderAccess` through the catalog grant; it uses the same unsaved-collection guard as Browse folder, while catalog discovery never mutates the active `PipelineWorkingCopy`. Changing the root reloads this temporary filesystem catalog, and so does every extraction run that published a clip: the GIF Extraction session emits `clipsPublished` once per run, and [`PipelineCatalogRefresher`](../../src/app/pipeline-catalog-refresher.ts) reloads the panel, so a first `extraction-tmp` or a root that did not exist at launch appears without a restart (the tree's disclosure state resets on reload); a future durable pipeline registry may replace its provider without changing the panel contract. The trusted extraction runtime also reads the root only to resolve the fixed `extraction-tmp` system pipeline. Zoom samples the audio preference for each new video; its local toggle stays local and the grid remains muted. See [`pipeline-catalog-runtime.spec.ts`](../../tests/unit/pipeline-catalog-runtime.spec.ts), [`pipeline-catalog-control.spec.ts`](../../tests/unit/pipeline-catalog-control.spec.ts), and [`settings.spec.ts`](../../tests/e2e/settings.spec.ts) for coverage.


[`FoldablePanelControl`](../../src/ui/foldable-panel-control.ts) owns each panel's folded and shown state, ARIA/inert state, focus transfer, and transition completion; a hidden panel reports no width and ignores fold requests. Its generation token rejects stale completions after reversal. `IAppScreen.panelContributions` supplies mountable content objects by panel id without shell knowledge of screen ids or access to control-owned DOM; captured ranges mount only for contributing GIF screens. A panel that has neither a contribution from the active screen nor page fallback content (`data-shell-panel-fallback`) is hidden with its rail and its width goes to the workspace; Pipelines always has its catalog fallback, while Clips has none, so it appears only on the GIF screens. `IAppScreen.initiallyFoldedPanelIds` names the panels folded on a screen's first entry; all others open. The shell normally restores each screen's last panel state on return. `IAppScreen.openPanelIdsOnEntry` overrides that saved state for panels a screen needs open whenever it is entered; Refine Gif uses it for Clips, while users may still fold Clips during that visit. CSS owns 240px/36px panel widths; `FoldablePanelControl` sets the 240/280ms closing/opening timing through `--panel-duration`; reduced motion completes immediately. The shell measures destination central width and wrapped command height once, calls the active screen's `onBoundsChanging(width, durationMs)` hook, and calls its `onBoundsSettled()` hook once after all moving panels finish. The GIF capture queue belongs to the GIF sessions' `CaptureQueue`, not to this shell mechanism.

`AppController` composes these controls. `CollectionScreen` forwards the shell's bounds hooks to its grid, and the grid observes its own root, skipping relayout while a Collection workspace resize is in progress. `CollectionFullScreenWorkflow` and `AppKeyDownHandler` receive the grid, Zoom and full-screen adapter themselves behind narrow interfaces; `CollectionFullScreenWorkflow` asks the shell to hide the window's shared parts (`setFullScreenLayout`) rather than touching the page. GIF Extraction, Refine Gif and Zoom edit mode's surface in the Zoom frame reparent one physical `FrameReviewPlayerControl` between their player hosts; the GIF screens make no player calls while inactive and remount it on activation. They do not reconstruct it, create a second playback engine, or add a second timeline. The player keeps ordinary playback/time seeking usable before exact preparation, switches the sole progress bar to canonical ordinals when ready, and routes held arrows through the session's bounded adjacent-step scheduler. Its movie full screen uses the player root, preserves that host's normal height while lifted, and exits before painting a different review session; it does not activate a new shell screen. [`ClipCollectionGridControl`](../../src/ui/clip-collection-grid-control.ts) opts into `coordinateWorkspaceLayout` in production: `beginWorkspaceResize` calculates the destination once and interpolates existing cards' positions/sizes; `endWorkspaceResize` reconciles actual bounds. Grid metric/current-column bookkeeping remains inside the grid controller. Normal allocated width excludes root padding; the original CSS-grid renderer remains available for other callers and Collection full screen. Collection full screen clears positioned card geometry and hides both panels, then restores their prior states on exit. App-wide utility closure and Activity auto-open suppression still apply to either full screen element. Tests: `foldable-panel-control.spec.ts`, `application-shell-control.spec.ts`, player/keyboard unit tests, grid integration tests, [`gif-movie-fullscreen.spec.ts`](../../tests/e2e/gif-movie-fullscreen.spec.ts), and [`gif-extraction-shell.spec.ts`](../../tests/e2e/gif-extraction-shell.spec.ts). Electron scenarios run with one Playwright worker because native windows share desktop focus and pointer state.

[`CurrentMovie`](../../src/app/current-movie.ts) owns one selected movie, its frame-review session and a source generation; [`CaptureQueue`](../../src/app/capture-queue.ts) owns the in-memory capture queue. [`CaptureThumbnails`](../../src/app/capture-thumbnails.ts) owns the draft/range thumbnail slots and their asynchronous cache-resource lifetime; `CaptureQueue` decides when workflow events replace, commit, refine, remove, or clear them. `RangeCaptureModel` implements the lock-only `Q`/`W`/`X` workflow: marks replace draft endpoints until `X`, `W` cannot modify a locked range, and the next `Q` begins a new draft. Endpoint values distinguish canonical exact frames from playback timestamps; either timestamp makes a locked range require refinement. Capture reads the same frame already displayed by `FrameReviewPlayerControl`, so playback marking does not pause while exact progress-bar scrubbing rejects late playback frames. Source replacement saves the draft with its movie and does not dispose the old review or thumbnails until the candidate opens; `GifExtractionSession.replaceSource` owns that order. During candidate opening, old captures remain visible but capture, refinement, and extraction are unavailable. Failed or cancelled opening leaves the old session intact; successful opening attaches the new review, resets the player timeline, then restores that movie's captures.

The active draft and locked unfinished captures are written as per-movie records under Electron `userData/clip-captures` by [`SavedCaptureCodec`](../../src/app/saved-capture-codec.ts), which owns the stored record format (its `exact-frame` endpoint kind is also checked by the desktop store) and restores a [`RangeCaptureModel`](../../src/domain/range-capture-model.ts) through `RangeCaptureModel.restore`; the domain model holds no storage format. A refused capture step returns a code from the domain (`RangeCaptureRejection`); [`CaptureRejectionText`](../../src/app/capture-rejection-text.ts) turns it into the status line, naming the key from `GIF_CAPTURE_KEYS` in [`gif-workflow-keyboard.ts`](../../src/ui/gif-workflow-keyboard.ts), which the composition root passes in. [`SavedCaptureQueuePersistence`](../../src/app/saved-capture-queue-persistence.ts) binds one source generation to its opaque movie reference, deduplicates asynchronous saves, tracks ranges whose saved frames no longer matched the movie when checked (stale ranges), and rejects late attach results after a movie switch invalidates that binding. `CaptureQueue` owns the live `RangeCaptureModel` and saves at queue transitions through its capture storage: `SavedCaptureStorage` wraps the binding, and `UnsavedCaptureStorage` is `GifExtractionSession`'s default when no storage is given. [`SourceFingerprint`](../../src/frame-review/model/source-fingerprint.ts) selects a queue from the native sampler's content digest, size, duration, stream and profile fields, without the cache build versions or source path. [`ClipCapturesStore`](../../electron/clip-captures-store.cjs) owns atomic bounded JSON, per-movie coalesced writes and reads ordered after pending writes; [`ClipCapturesIpcBoundary`](../../electron/clip-captures-ipc.cjs) keeps saved paths in main and grants the renderer only opaque movie references for an explicitly opened source. `AppController` wraps the renderer-facing [`ElectronClipCapturesStoreService`](../../src/adapters/electron/electron-clip-captures-store-service.ts) in `SavedCaptureStorage` and gives it to `GifExtractionSession`. The session also receives the `ActivityReporter`, the Activity log and diagnostics for its reporting, and two awaited collaborators behind narrow interfaces: a publication listener (`OpenFolderRefresher`, so extraction continues only after the open folder has reacted) and capture positioning (the shared player, whose failure the session reports). Startup leaves the movie session empty. Start/End marks and locked ranges save asynchronously and restore on matching content when the user explicitly opens that movie, including after restart. When saved captures exist, GIF Extraction displays the exact frame after the last saved range end or the latest unfinished draft endpoint, clamping at the final frame. Exact saved endpoints contain ordinal, decoded-frame hash and review time; saved draft endpoints are checked by Lock itself, and locked endpoints by Refine and Extract themselves, so no caller runs the check; they use BestSource's metadata-only `identity` command without seeking playback. The separate `thumbnail` command redraws saved start frames without changing the player's or adjacent-step cursor. Extraction status and thumbnail resources remain session-only; fully published ranges leave the durable unfinished queue.

[`RangeRefinementDraft`](../../src/app/range-refinement-draft.ts) is a one-range staging object owned by [`RangeRefinement`](../../src/app/range-refinement.ts). It preserves an inexact or exact captured range, focuses one endpoint at a time (Start first on entry), and accepts only exact displayed captures from the current source generation. The Clips panel keeps the complete queue visible and offers Refine and double-click entry for every captured range. The draft's `unlockedChanges` lists staged endpoints whose frames differ from the captured range. Leaving Refine while that list is non-empty asks first: Back and choosing another range in the Clips panel call [`RefineLeaveWorkflow.confirmDiscard`](../../src/app/refine-leave-workflow.ts), and any other screen change (workspace selector, Settings, a catalog Load) is held by [`RefineScreenLeavePolicy`](../../src/app/refine-screen-leave-policy.ts), whose refusal the shell reports as `screenChangeRefused` so the same workflow asks and completes the change. [`DiscardRefinementDialogControl`](../../src/ui/discard-refinement-dialog-control.ts) names what would be lost; Discard abandons the staging, Keep editing or Escape keeps it and returns focus. `GifWorkflowKeyboard` ignores keys pressed inside a dialog. The underlying captured range remains unchanged until Lock. Start/End cards jump to their stored endpoints; Q/W stage the currently displayed exact frame. `X` atomically replaces the same opaque queue entry only when both exact ordinals form a valid inclusive range; leaving the screen abandons staging without changing the queue. An unchanged exact lock preserves its extraction outcome. A changed lock resets that range's extraction outcome to pending; earlier published media remain saved, and extraction is again an explicit action. Active extraction and unresolved collection publication block changed locks until completion or retry. Source replacement or range removal invalidates an active refinement. The contextual Refine Gif screen enters exact scrub near the stored endpoint through the shared player and restores queue focus on return. `E` extracts the committed current exact range; `Extract all` snapshots all currently eligible exact ranges and continues after individual failures. Clips already in a folder are refined in [Zoom edit mode](#zoom-edit-mode), not here.

[`ClipExtractor`](../../src/business-logic/clip-extractor.ts) validates exact-only requests before crossing [`IClipExtractionService`](../../src/business-logic/clip-extraction-service.ts). [`ClipExtractionWorkflow`](../../src/app/clip-extraction-workflow.ts) owns single/batch progress, cancellation, per-range outcomes, and publication retry without re-encoding; [`ExtractionPublisher`](../../src/app/extraction-publisher.ts) owns lazy reuse/creation of the movie-stem collection and emits a collection-published event only after durable membership persistence. Extraction always publishes to `extraction-tmp`. The publisher reads only its target collection, with `CollectionDescriptionValidator` (the same rules as opening a folder): an empty file is an empty collection, and a file with duplicate entries refuses the extraction before anything is encoded rather than being rewritten. `Collection.withExtractionOutput` decides where a new output goes. [`OpenFolderRefresher`](../../src/app/open-folder-refresher.ts) owns the response policy: it re-enumerates a matching, already-open clean folder immediately, or defers one refresh until the active Collection is successfully saved and Zoom edit mode is not active (`afterCollectionSaved`, `afterZoomEditModeEnded`). [`FolderSelectionWorkflow`](../../src/app/folder-selection-workflow.ts) owns active-folder reload, including preservation of the selected collection. The renderer sends only opaque source/destination handles and validated names. [`ClipExtractionRuntime`](../../electron/clip-extraction-runtime.cjs) resolves the original prepared-review source and selected stream in the main process and builds the source-info record before encoding. The encoding itself is [`ExactRangeEncoder`](../../electron/exact-range-encoder.cjs), one instance that `main.cjs` injects into both extraction and `EditedClipSaver`. Its one `output` option names what it makes: `cut-with-sound` (the default, which extraction uses), `silent-cut` or `forward-then-backward`; its FFprobe reads (the cut's boundary times when no index gives them, and the check of the encoded media) belong to [`ExactRangeProbe`](../../electron/exact-range-probe.cjs). For an unchanged original source, [`FrameReviewHost`](../../src/frame-review/host/frame-review-host.ts) reads a bounded ordered frame-timestamp window from the already open BestSource index; the encoder seeks near that window, selects by indexed integer PTS, verifies every selected source timestamp and final frame count, and muxes nearby audio. Integer PTS selection avoids floating time-boundary rounding; missing or ambiguous index timing, normalization, or failed verification still uses the original exact full-decode route. The runtime publishes `<collection-name>-NNN.mp4` exclusively without overwrite. Main-process progress crosses IPC with an operation ID through [`CorrelatedIpcReplies`](../../electron/correlated-ipc-replies.cjs), as for Zoom edit saves and previews; the adapter discards stale events. Main-process failures that cross IPC are shaped by [`OperationResult`](../../electron/operation-result.cjs). The shared Clips panel and Refine Gif show current clip, stage, encoded frames when available, and Cancel. Cancel aborts active media work and stops later ranges; a clip already created is published or left in recoverable publication-failed state. Collection persistence is atomic, output allocation is serialized per destination collection, and a membership-save failure can be retried without launching FFmpeg again.

Start thumbnails are ephemeral renderer-generated PNGs. [`ElectronThumbnailCacheService`](../../src/adapters/electron/electron-thumbnail-cache-service.ts) bounds and validates PNG payloads, exposes only Blob URLs plus opaque ids, and revokes URLs it owns. [`ThumbnailCacheRuntime`](../../electron/thumbnail-cache-runtime.cjs) owns `userData/cache/thumbnails`, validates ids and payloads again, and never returns a path. Electron clears that directory at startup and on normal shutdown after native review hosts close, and `ZoomEditPreviews` does the same for `userData/zoom-edit-previews`; persistent `frame-index-cache`, `playback-proxy-cache`, and `exact-review-proxy-cache` entries are unaffected. `GifRangesPanelControl` renders the complete shared queue with start pictures, exact/inexact labels, accessible Refine entry points, and the selected range highlighted; it does not own the queue. Tests: range/refinement/session/cache unit tests and panel/screen integration tests. The remaining native GIF output checks are in [`gif-extraction-output.spec.ts`](../../tests/e2e/gif-extraction-output.spec.ts).

Renderer shutdown is ordered but remains best-effort because a browser page cannot hold Electron quit open. [`ApplicationShutdownCoordinator`](../../src/app/application-shutdown-coordinator.ts) first disposes `AppKeyDownHandler`, Collection full screen and the shell, then starts workflow disposal; in the same `pagehide` handler `ApplicationEventController` removes its own listeners. Disposal awaits Zoom edit mode's and the GIF Extraction session's `dispose()` (a running edited-clip save is cancelled) so extraction cancellation, movie review disposal, subscription detachment, and thumbnail cleanup precede destruction of the shared player and global controls. `GlobalUtilityCoordinator`'s document and resize listeners and the grid's `ResizeObserver` stay live until then; they only touch their own controls, and no input reaches a page that `pagehide` is unloading. The trusted process is the authoritative close barrier: [`electron/main.cjs`](../../electron/main.cjs) prevents final quit until frame-review hosts, the clip-extraction runtime, `EditedClipSaver` and `ZoomEditPreviews` have disposed, then removes ephemeral thumbnails. Active FFmpeg/native work receives abort, operation-owned temporary directories are removed, and validated prepared-review caches deliberately survive shutdown.

The main-process quit barrier also awaits pending capture-store writes before closing; per-movie `clip-captures` records survive app restarts.

### Source Info

Source info is the bounded `clip-sandbox.prov.v1` MP4 movie tag. Its record rules belong to [`SourceInfo`](../../electron/clip-provenance/source-info.cjs), built only through its factories; [`Mp4Provenance`](../../electron/clip-provenance/mp4-provenance.cjs) only turns a `SourceInfo` into a tag value (`tagValueOf`, at most 4,096 bytes), writes it and reads it back. A record names the movie (bare file name and sampled source fingerprint, never the private path), the range (`start`, `end`, inclusive canonical ordinals, with optional `startTimeUs`/`endTimeUs` in movie microseconds) and, separately, one to four reference frames (ordinal and 16-hex frame check value), which need not be the range's ends. Records are written as version 2; a version 1 record reads as a range whose reference frames are its two ends and has no times. A third shape keeps only the movie: a version 2 record with `sourceMovie` and neither `sourceFrameRange` nor `referenceFrames` (one without the other is invalid). Loopify writes it (`limitedTo('movie-only')`, chosen by `ZoomEditComposition.sourceInfo`); it is a plain `SourceInfo`, whose `ranged()` answers `null` and whose `trimmed` keeps it as it is, the glyph shows its movie, and Zoom edit mode treats such a clip as trim-only (`openWindow` answers `movie-only` without looking for the movie). Builds older than this shape read it as no source info. `SourceInfo.forMovieRange` builds a complete record (a `RangedSourceInfo`) and `SourceInfo.forMovie` a movie-only one. On a `RangedSourceInfo`, `trimmed(startOffset, endOffset)` shifts the range of a clip cut without its movie while keeping its reference frames and the original ends' times (which only place a movie window), `exactTimeUsOf` answers a stored time only while the reference frames are still the range's two ends; the static `SourceInfo.timeUsOf` gives the time a record stores for a frame. For new MP4 output the extraction runtime gets trusted endpoint identities from the prepared BestSource index and writes both ends as reference frames with their review times. A metadata-specific mux failure retries with the encoded video and no tag; a readback failure reports a warning after successful media and Collection publication. Existing clips and clips without valid provenance remain loadable. Every read of the tag (read-back, Zoom edit requests and saves, the folder read below) goes through [`Mp4MetadataTagReader`](../../electron/clip-provenance/mp4-metadata-tag-reader.cjs), which walks the MP4's `moov/udta/meta` boxes directly with bounded reads and no FFprobe: it returns `null` for no tag or a malformed file and throws only when the file cannot be read. `Mp4Provenance.canBeTagged` limits source info to `.mp4` files, and `SourceInfo` validation rejects a movie name containing a folder separator. Fixtures with known tags live in [`tests/fixtures/source-movie/`](../../tests/fixtures/source-movie/README.md).

Collection cards mark clips that have source info. [`ClipSourceMovieRuntime`](../../electron/clip-source-movie-runtime.cjs) serves `clip-sandbox:clip-source-movies-read`: it checks the window's folder grant and, through [`ClipFilenameRule`](../../electron/clip-filename-rule.cjs) (which Zoom edit mode's `GrantedClipResolver` shares), plain video file names before reading anything, reads a few clips at a time and answers each with the movie's file name, `none` or `unreadable`; [`ElectronClipSourceMovieService`](../../src/adapters/electron/electron-clip-source-movie-service.ts) validates the answer into a [`ClipSourceMovieReport`](../../src/app/clip-source-movie-service.ts). Nothing is cached: the tag travels in the file. [`ClipSourceMovieRefresher`](../../src/app/clip-source-movie-refresher.ts) reads all of the open pipeline's clips after `FolderSelectionWorkflow` loads or re-lists a folder (including view switches, which re-list from disk) and one clip after `CreatedClipInsertion` (Keep both) or `ClipFileReplacement` (Replace) shows a new file; it applies an answer only while the same `Pipeline` is open and no newer folder read began, keeps each clip's previous value until its answer arrives, and reports read failures as one Activity note, never an error (a failed read request also goes to the folder's error log); after `dispose()` at shutdown it starts no reads and ignores answers. `FolderSelectionWorkflow`, `CreatedClipInsertion` and `ClipFileReplacement` reach it through their own `IFolderClipSourceMovies`, `ICreatedClipSourceMovie` and `IReplacedClipSourceMovie` interfaces. `ClipCollectionGridControl.refreshSourceMovieGlyphs` redraws the corner film glyph and the card's `aria-description` ("From <movie>", worded by `ClipLabelFormatter`) in the visible and cached views; the glyph hides with the titles, so Zoom and Collection full screen follow the titles setting. See [`docs/specs/clip-source-movie-glyph-spec.md`](../specs/clip-source-movie-glyph-spec.md) for the agreed behavior and later parts of the direction.

4. [`electron/zoom-edit-sources.cjs`](../../electron/zoom-edit-sources.cjs), [`electron/staged-edit-resolver.cjs`](../../electron/staged-edit-resolver.cjs), [`electron/edited-clip-saver.cjs`](../../electron/edited-clip-saver.cjs), [`electron/edited-clip-placement.cjs`](../../electron/edited-clip-placement.cjs) and [`electron/zoom-edit-previews.cjs`](../../electron/zoom-edit-previews.cjs)

Flow in the renderer:

1. Entry: only from Zoom. Zoom's edit menu (`ZoomEditMenuControl`) lists Refine and Loopify, and R and L in Zoom (`ZOOM_EDIT_ENTRY_KEYS`, read by `AppKeyDownHandler`) do the same; all go through `ZoomWorkflow.enterEditMode(entry)` to `ZoomEditModeWorkflow.enterFromZoom(clip, entry)`, Loopify with Loopify already staged. The grid's menu offers neither edit. `ZoomWorkflow` reaches the mode only through the `enterZoomEditMode` callback the composition root supplies. The mode needs an open folder, is unavailable in Collection full screen, and takes `muted` from Zoom's audio state on entry. It exists only when the frame-review, Zoom edit source, save and preview services exist; otherwise Zoom offers no edit menu and R and L do nothing.
2. Surface: `ZoomOverlayControl.showEditSurface` replaces Zoom's video with an edit surface holding the shared player (`mountInZoomEdit`) and a hint line under it (`showEditHint({ keys, status })`); `showEditPreview(mediaSource)` lays a silent looping `<video>` over the player and `hideEditPreview` removes it; `hideEditSurface` removes everything. The overlay reports a backdrop click as `closeRequested`: `ZoomWorkflow` closes Zoom only while the mode is inactive, and `ZoomEditModeWorkflow` otherwise leaves the mode (asking first) and then closes Zoom. `ZoomWorkflow.openClip` refuses while the mode is active, so Zoom's navigation is suspended.
3. Keys: `ZoomEditModeKeyboard` maps Space, Left/Right, top-row digits 1–5 by key position, Q/W/A/S/Z/L/X and Escape to commands; a held key requests its command once, except Left/Right, which send `press-step` on the first keydown and `release-step` on keyup or window blur. Key names live in `ZOOM_EDIT_MODE_KEYS`, which the hint text and the keyboard map's `Zoom edit` group (`ZOOM_EDIT_MODE_SHORTCUTS`, part of `COLLECTION_SHORTCUTS`) share; the entry keys R and L are listed in the `Zoom` group (`ZOOM_EDIT_ENTRY_SHORTCUTS`). T, which shows or hides titles, is handled before the mode's keys. The workflow passes each command to the session and shows a refusal's reason in the hint line; all wording is in `ZoomEditModeText`, which also lists the staged edits and what they cost ("Refine + Loopify staged · saved without sound"). X waits for commands already pressed (not a held step) before checking what is staged, and asks the session's `saveRefusal()` why it cannot save yet.
4. Session: `ZoomEditModeSession.begin` opens the clip itself at once (its own `CurrentMovie`) so trimming never waits for the movie, and for a clip with source info starts a `ZoomEditMovieWindow` in the background when the entry edit needs the source movie (Refine); otherwise it starts it the first time a key does Refine's work (Q, W, or a step or jump whose target is past the clip's first or last frame, refused as not available yet while the movie is found), so a Loopify-only session never looks for the movie. Once the clip is exact-ready it shows the clip's exact first frame, unless Space was pressed while the clip was shown. Commands run one at a time and answer done, refused with a reason, or failed; the snapshot is `{ picture, extension, extensionPending, range, preview }`. The session keeps a list of staged edits: `StagedRefine` reads the session's current range and is staged when it differs from the whole clip; `StagedLoopify` owns the switch L toggles, started from the entry. `stagedEdits()` composes the staged ones into a `ZoomEditComposition`, `stagedChanges()` lists what leaving would discard, and `saveRefusal()` answers a not-ready clip or the composition's refusal of the range. The staged range is a `RefineRange` in clip-relative frame numbers (0 is the clip's first frame; negative numbers and numbers past its last frame are movie frames), so it survives the switch from the clip to the window; `RefineRange` owns the limits (the clip's frames, or the anchored window's frames within one minute of the clip's ends) and the refusal reasons. While the mode is active the session decides which review the shared player shows and detaches it on dispose. Q/W/A/S during playback pause first and act on the exact frame shown; Z during playback starts the loop; steps and jumps stop at the limits. `pressStep` steps once at once and, through [`HeldStepRepeat`](../../src/app/held-step-repeat.ts), repeats until `releaseStep`, another held step or a step that does not succeed; it uses the GIF player's held-step timing (`HELD_STEP_TIMING` in [`adjacent-step-scheduler.ts`](../../src/frame-review/adjacent-step-scheduler.ts)), and each repeat is an ordinary queued step. `pause()` ends a held step and pauses playback; the workflow calls it before the save and discard dialogs. `stagedSelection()` gives the range in the shown source's numbering with its review session id.
5. Loop preview: when the staged edits play backward (Loopify), Z pauses the player and shows the session's `ZoomEditLoopPreview`, which renders a preview of the staged selection through [`ElectronZoomEditPreviewService`](../../src/adapters/electron/electron-zoom-edit-preview-service.ts) (progress in the hint line) and keeps it for those edits: the next Z hides it, the one after shows it again at once. Space stops it and leaves the player paused on the frame it showed (playing on would run past the clip in its movie window); any other key hides it; a change of the staged range, of Loopify or of the shown source (the switch to the window) drops it and releases its file. A failed render is reported and said in the hint line until the next key, and Z then loops the exact range forward. Without Loopify, Z loops the exact range as before. A range the staged edits refuse (one frame with Loopify) is refused before any preview.
6. Movie window: `ZoomEditMovieWindow` owns finding, preparing and anchoring the window (`finding-movie`, `preparing-window`, `anchored`, or `cancelled`, `none`, `movie-only`, `not-found`, `failed`). When no reference frame is found it asks for a wider window, at most twice, naming the previous window. Once anchored and the clip is ready, the session switches the player to the window at the same displayed frame.
7. Leaving: Escape returns to Zoom on the same clip; a second Escape closes Zoom. Leaving with staged edits (Escape, closing Zoom, another screen, a folder load or a collection switch) pauses the player and asks through `DiscardRefinementDialogControl.forZoomEdit`, naming what the session's `stagedChanges()` lists (Loopify and the changed ends); the clip stays paused whatever the answer. `ZoomEditModeLeavePolicy` holds every screen change away from Collection while the mode is active, staged edits or not, so the mode ends and releases the shared player before another screen attaches it; the workflow asks only when something is staged and then completes the change. `FolderSelectionWorkflow` calls `ZoomEditModeWorkflow.confirmLeave()` before folder loads and collection switches, and `OpenFolderRefresher` defers re-listing while the mode is active and runs it after the mode ends (`afterZoomEditModeEnded`).
8. Saving: the workflow pauses the player, then `EditedClipSaveWorkflow` asks Keep both, Replace or Cancel (`SaveEditsDialogControl`, which names the edited clip and repeats any loss, such as the sound), waits while the movie is still being found or prepared if the staged edits need the source movie (Loopify alone never waits), then saves the staged selection with the staged edit names (`edits`) through `IEditedClipSaveService` ([`ElectronEditedClipSaveService`](../../src/adapters/electron/electron-edited-clip-save-service.ts)) with progress in the hint line. Loopify alone saves the whole clip. Escape cancels the wait or the save and keeps the staged edits. After saving the mode ends and Activity reports the outcome and any notice. Keep both goes through [`CreatedClipInsertion`](../../src/app/created-clip-insertion.ts): right after the original in a saved collection's view (the view becomes unsaved), in name order in the folder's full list, then the source movie is read and Zoom opens the clip. Replace goes through [`ClipFileReplacement`](../../src/app/clip-file-replacement.ts): `PipelineWorkingCopy.replaceClipFile` (`Pipeline.replaceVideoFile`, `Clip.replaceFile`) keeps the clip's id and renames it in every collection, `CollectionFileWriter` rewrites those files (a failed write restores that collection in memory and is reported), every grid view is rebuilt, the source movie is read again and Zoom shows the clip; a rename alone leaves the view saved. The folder re-listing runs only after the saved clip is in the views.
9. Every media address the main process lists or saves carries `?modified=<mtime>` (`mediaSourceOf` in [`electron/folder-entry.cjs`](../../electron/folder-entry.cjs)), so a file replaced under the same name is never shown from the renderer's media cache, including after a view switch re-lists the folder.

Main process:

1. [`ZoomEditSources`](../../electron/zoom-edit-sources.cjs) serves `clip-sandbox:zoom-edit-open-clip`, `clip-sandbox:zoom-edit-open-window` and `clip-sandbox:zoom-edit-anchor-window`, reached through [`ElectronZoomEditSourceService`](../../src/adapters/electron/electron-zoom-edit-source-service.ts). Every Zoom edit request names a clip through [`GrantedClipResolver`](../../electron/granted-clip-resolver.cjs) (folder grant, `ClipFilenameRule`, is a file). Opening the clip registers it with the window's `FrameReviewHost`. Opening a window reads the clip's `SourceInfo` (a movie-only record answers `movie-only`), finds the movie with [`SourceMovieLocator`](../../electron/source-movie-locator.cjs) (where [`LocatedMovieStore`](../../electron/located-movie-store.cjs) last found it, the remembered capture-store path, then granted and catalogued pipeline folders with a matching file name first, then the movie picker; a file whose size differs from the fingerprint's `sourceBytes` is skipped before any fingerprinting; it answers `located` or `cancelled`, remembers the path in `LocatedMovieStore` and registers nothing), places the window, gets it from the cache and answers a source handle and an opaque window id, never a path. Every window request asks the locator; a repeat lookup asks the user nothing and measures nothing, because `SourceMeasurementCache` answers the fingerprint check of an unchanged file measured by the same tools (it still lists the pipeline folders). `LocatedMovieStore` keeps at most 32 movies in `<userData>/located-movies.json`, keyed by a hash of the fingerprint; its paths never leave the main process. Window records, with the movie identity and anchor, stay in the main process and are forgotten when the app window closes. A widening request names the previous window, which must be the same clip's window one step narrower.
2. [`MovieWindowPlacement`](../../electron/movie-window-placement.cjs) places the clip by its stored times, else the movie's cached index (`FrameReviewHost.cachedFrameTimesUs`), else an estimate from [`MovieFrameRateProbe`](../../electron/movie-frame-rate-probe.cjs) (FFprobe's average frame rate of the selected stream, else its base rate). The margin on each side is the one-minute extension limit plus 15 s, doubled per widening step; clips spanning more than ten minutes are refused.
3. [`MovieWindowCache`](../../electron/movie-window-cache.cjs) keeps windows under `<app-folder>/movie-window-cache/<key>/window.mkv` with a manifest, keyed by movie fingerprint and window bounds. It cuts with FFmpeg stream copy (the selected video stream and the first audio track) into a temporary file renamed into place; callers asking for the same window share one cut. It keeps at most 10 windows by last use and evicts older ones together with their prepared-review entries (`forgetPreparedReview` on the runtime's maintenance host), skipping windows still being cut; validated windows survive restarts. A window in use is marked used only when opened.
4. [`MovieWindowAnchor`](../../electron/movie-window-anchor.cjs) numbers the window by finding a reference frame's check value in the exact-ready window session (`FrameReviewHost.findFrameByCheckValue`), never by times. [`AnchorSearchOrder`](../../electron/anchor-search-order.cjs) lists every window frame once: outward from the estimate, or for a widened window the added stretches nearest the previous window first. The answer is `clipStartFrame` and the earliest and latest window frames within one minute of the clip's original ends, or `not-found` when no reference frame is found or the clip does not fit in the window.
5. `StagedEditResolver` checks every save and preview request and answers the cut and its `ZoomEditComposition` (see Stable Concepts). A cut of a window uses [`AnchoredMovieWindow`](../../electron/anchored-movie-window.cjs) from `ZoomEditSources.anchoredWindow`, refuses a window of another clip or a range beyond the extension limit, and knows whether the range is the whole clip (`showsWholeClip`).
6. [`ZoomEditSaveIpcBoundary`](../../electron/zoom-edit-save-ipc.cjs) serves `clip-sandbox:zoom-edit-save` and `clip-sandbox:zoom-edit-cancel-save`, with progress on `clip-sandbox:zoom-edit-save-progress`, correlated by operation id ([`CorrelatedIpcReplies`](../../electron/correlated-ipc-replies.cjs), shared with the preview boundary). [`EditedClipSaver`](../../electron/edited-clip-saver.cjs) never accepts a record from the renderer; `StagedEditResolver` refuses a request with nothing staged. A cut of the clip itself writes the clip's own `SourceInfo.trimmed(...)`, or no record for an untagged clip; a cut of a window writes `SourceInfo.forMovieRange` in movie numbering with the new ends as reference frames, with times only when exact (the clip's stored times while they are still exact, else the movie's cached index, else none). The record is then limited to what the composition allows (`limitedTo`: movie only with Loopify). Encoding uses the shared `ExactRangeEncoder` in a temporary workspace inside the clip's folder, with the `output` the composition calls for: `forward-then-backward` when it plays backward (the exact cut, then a [`ForwardThenBackwardFilter`](../../electron/forward-then-backward-filter.cjs) step checked for twice the cut frames, without sound), else `cut-with-sound` or `silent-cut` as it keeps sound or not.
7. [`EditedClipPlacement`](../../electron/edited-clip-placement.cjs) never overwrites a file. Keep both creates `<stem><suffix>.mp4` with the composition's suffix (`-refined`, `-looped`, `-refined-looped`), then `<stem><suffix>-2`, and so on. Replace runs one at a time: it targets the clip's name (for a non-MP4 clip `<stem>.mp4`, kept as Keep both with notice `name-taken` if that name exists), writes a per-operation `<stem>.<random>.refining` file that no listing shows as a video, moves the original to the Recycle Bin and only then renames. A refused Recycle Bin move keeps both (`recycle-bin-refused`); after the original is in the Recycle Bin, a taken name or failed rename falls back to the Keep both name (`replaced` with a notice), and as a last resort the temporary file is kept and the save reports it.
8. [`ZoomEditPreviewIpcBoundary`](../../electron/zoom-edit-preview-ipc.cjs) serves `clip-sandbox:zoom-edit-preview` (progress on `clip-sandbox:zoom-edit-preview-progress`) and `clip-sandbox:zoom-edit-release-preview`. `ZoomEditPreviews` resolves the request with Loopify as its only edit (the preview request carries no edit list), selects the staged frames by their times in the source the review indexed, and renders them at most 960 pixels wide, forward then backward, without sound, into its folder; it answers a media address, never takes a path. A new preview of an app window stops and removes that window's previous one; release, an app window closing, startup and quit remove them.

### Activity and Errors

[`ActivityLogger`](../../src/app/activity-logger.ts) is the session-history owner. Activity producers receive its instance, an adapter to its typed `log` contract, or an [`ActivityReporter`](../../src/app/activity-reporter.ts) (success/progress/failure over the logger) from `AppController`; they do not call the panel. Reporting follows the layer: app-layer components (workflows, sessions, policies) receive the reporter injected, while UI controls never report themselves; they emit failure events, and [`ControlFailureReporting`](../../src/app/control-failure-reporting.ts) decides whether each goes to Activity or only to the diagnostics log. There is no global reporter. [`ActivityPanelAutoOpenPolicy`](../../src/ui/activity-panel-auto-open-policy.ts) answers whether an error may open the panel. Entries have a message, optional extra text, and ordered named fields for variable detail. Errors also carry affected-operation/recovery text, optional technical details, and an optional retry capability supplied by the caller. Stable error ids support explicit resolution: `ActivityReporter.failure` returns the id and `resolveFailure` resolves it, which `ControlFailureReporting` uses to resolve Pipelines list-load errors (`failed` with kind `catalog`, not a pipeline's contents) once the catalog control reports `loaded`. Notes (`information` entries) are history only; they do not count as errors or open the panel. Retention keeps the newest 50 non-error/resolved entries plus every unresolved error; bulk clear preserves unresolved errors, while each error offers explicit dismissal. No notification database or global singleton is added.

The control listens to logger changes and owns history keyboard navigation, native wheel scrolling without scrollbar chrome, detail expansion and local copy/retry interaction. The application injects clipboard writing directly; failures stay inside the entry. Settings supplies a retry that reapplies only the failed preference against the current committed settings, returning a typed failure to the existing entry. Folder/collection/video-edit errors provide available context without automatically replaying destructive operations. Tests: `activity-logger.spec.ts`, `activity-indicator-control.spec.ts`, `settings-workflow.spec.ts`, app-controller integration protection checks and [`activity.spec.ts`](../../tests/e2e/activity.spec.ts).

### Folder Load

Read these first:

1. [`electron/preload.cjs`](../../electron/preload.cjs)
2. [`src/adapters/electron/electron-folder-service.ts`](../../src/adapters/electron/electron-folder-service.ts) and, for Pipelines, [`electron-pipeline-catalog-service.ts`](../../src/adapters/electron/electron-pipeline-catalog-service.ts)
3. [`src/app/folder-selection-workflow.ts`](../../src/app/folder-selection-workflow.ts) and [`src/app/collection-view-workflow.ts`](../../src/app/collection-view-workflow.ts)
4. [`src/business-logic/PipelineFactory.ts`](../../src/business-logic/PipelineFactory.ts)
5. [`src/domain/pipeline.ts`](../../src/domain/pipeline.ts)

Flow:

1. `FolderSelectionWorkflow` handles the toolbar's browse request or a Pipelines catalog load (behind the unsaved-changes prompt, and first leaving Zoom edit mode if it is active), and the renderer asks the preload bridge to pick a folder,
2. Electron main enumerates top-level files from the chosen folder and returns lightweight metadata plus collection-file text and video media URLs (each carrying `?modified=<mtime>`); absolute paths remain an existing filesystem/edit compatibility field but do not enter the renderer frame-review service contract,
3. `ElectronFolderService` converts those records into plain [`FolderEntry`](../../src/business-logic/folder-entry.ts) values (name, type, media address, desktop path, and text for `.txt` files),
4. `PipelineFactory.buildPipeline(...)` classifies videos and `.txt` collection files, reads each collection from its entry's text through `CollectionTextFormat`, turns videos into `ClipSource` values, then builds the durable `Pipeline`,
5. the initial active selection is pipeline mode, and `PipelineWorkingCopy.loadPipeline(...)` materializes a runtime `ClipSequence` over canonical clips, creating generated ids only for video files not yet represented by a runtime `Clip`,
6. collection selection uses `Pipeline.getCollectionByFilename(...)` plus `PipelineWorkingCopy.materializeSelection(...)` / `activateSelection(...)` to re-materialize a runtime `ClipSequence` from the chosen `Collection` against the current pipeline's canonical clips,
7. the grid controller renders that runtime sequence and owns card DOM, selection UI, drag/drop, media-element lifecycle, and card-video metadata capture.
8. flows that durably add files, such as exact extraction, publish an explicit completion event rather than watching the filesystem; `OpenFolderRefresher` re-enumerates an already-open matching clean folder, or defers the refresh until its active Collection save succeeds and Zoom edit mode has ended.

### Selection Switching and Persistence

Read these first:

1. [`src/domain/pipeline.ts`](../../src/domain/pipeline.ts)
2. [`src/domain/collection.ts`](../../src/domain/collection.ts)
3. [`src/adapters/electron/electron-folder-file-service.ts`](../../src/adapters/electron/electron-folder-file-service.ts)
4. [`src/app/collection-view-workflow.ts`](../../src/app/collection-view-workflow.ts), [`src/app/collection-save-workflow.ts`](../../src/app/collection-save-workflow.ts), [`src/app/add-to-collection-workflow.ts`](../../src/app/add-to-collection-workflow.ts), [`src/app/trash-clips-workflow.ts`](../../src/app/trash-clips-workflow.ts) and [`src/app/collection-file-writer.ts`](../../src/app/collection-file-writer.ts)

Flow:

1. `Pipeline` owns the current folder's available video files, canonical runtime clips, and saved collections,
2. `PipelineWorkingCopy` owns the active selection; `activeCollection === null` means pipeline mode,
3. switching selections re-materializes a runtime `ClipSequence` through `PipelineWorkingCopy`, which delegates to `Pipeline.materializePipeline(...)` or `Pipeline.materializeCollection(...)` and reuses canonical `Clip` objects so loaded metadata survives view switches,
4. saving an existing collection writes the active `ClipSequence` back to that collection's backing file,
5. saving from pipeline view creates a new `Collection`; the pipeline view itself is never persisted,
6. add-to-collection, save, and Recycle Bin flows are orchestrated by `AddToCollectionWorkflow`, `CollectionSaveWorkflow` and `TrashClipsWorkflow` (files go to the operating system trash through `shell.trashItem` in the `clip-sandbox:trash-files` IPC handler, never `unlink`; under `CLIP_SANDBOX_E2E=1` to the test profile's `TestRecycleBin`): `Pipeline` owns the durable in-memory mutation rules, `PipelineWorkingCopy` owns active-sequence state and dirty tracking, and `CollectionFileWriter` performs the raw collection-file writes through [`ElectronFolderFileService`](../../src/adapters/electron/electron-folder-file-service.ts). A new collection name gets two separate checks: `CollectionNameValidator` decides whether the name is valid, and `Pipeline.hasCollectionWithFilename` (through `NewCollectionNameCheck`) decides whether it already exists. Save as collection is awaitable and settles as `saved`, `cancelled` or `failed`, which the unsaved-changes prompt and the Recycle Bin preflight use before continuing; its panel is not modal, so a request made while it is open takes it over and the earlier caller's wait settles as `cancelled`, leaving only the latest flow to resume. A Recycle Bin request keeps the folder it was built for and moves nothing if another folder is open when it is confirmed,
7. remove-from-view is only a collection-view behavior; in pipeline view, the Delete key routes to the move-to-Recycle-Bin flow.

Flow:

1. the grid controller owns card rendering, reorder drag/drop, and metadata updates; its selection lives in [`GridSelection`](../../src/ui/grid-selection.ts), which keeps the selected clips together with the anchor a Shift range starts from (the clip last selected or toggled on its own). A right-click on a clip outside the selection makes it the selection before `contextMenuRequested` is emitted, while a clip inside a multi-selection keeps it,
2. card videos play the clip's `ClipSource` media address, the `file://` URL its `FolderEntry` carries; the app has no blob-URL fallback, and only the renderer test harness substitutes blob URLs,
3. rendered card videos populate `Clip` duration and intrinsic dimensions through `loadedmetadata`; `GridVideoMetadataTracker` tracks active-sequence metadata completion/failure so the normal grid can perform at most one metadata-based correction relayout,
4. `ClipCollectionGridControl` owns a per-loaded-pipeline grid-view cache keyed by pipeline view or collection filename; switching views reuses cached, still-mounted grid/card/video DOM when the ordered clip ids still match, with inactive grids kept invisible and out of flow, while `CollectionViewWorkflow` and the mutating workflows only supply view keys and invalidate views after sequence membership/order changes. Every card decodes its full-size clip, and the video decoder keeps up with only a few dozen at once, so previews play only on the cards the shown view displays: a view left in the cache and cards Collection full screen hides are paused, and `holdPreviews()` pauses them all until the returned release is called; `ZoomWorkflow` holds while Zoom is open and `CollectionScreen` from construction until it is shown and again while another screen is,
5. `DisplayLayoutRules` owns normal and fullscreen grid calculations; normal scoring maximizes expected contained video area using known clip dimensions with a deterministic fallback aspect ratio,
6. reorder emits ordered clip ids as a grid event to `CollectionViewWorkflow`, which delegates active `ClipSequence` mutation and dirty-state tracking to `PipelineWorkingCopy`; drag-and-drop and Alt+Arrow share one move path in the grid. The selector's Unsaved marker and the toolbar's Save button follow `hasDirtyClipSequenceChanges` through `CollectionViewWorkflow.refreshSelector`/`refreshToolbar`, and Save emits the same `saveRequested` as Actions → Save,
7. keyboard: the grid keeps one card as the Tab stop (the last focused, else the first selected, else the first card); [`GridNavigationRules`](../../src/ui/grid-navigation-rules.ts) maps arrow keys to card indexes using the applied column count. A plain arrow focuses the card and selects only it, Ctrl+arrow moves the focus and keeps the selection, Shift+arrow selects the range from the anchor, Alt+arrow moves the card. T (in `AppKeyDownHandler`, also in Zoom and Zoom edit mode, not in full screen) does what the toolbar's Hide titles does: `CollectionViewWorkflow.toggleTitles` hides the grid's titles and Zoom's title together. Shift+F10/Menu emit `contextMenuRequested` with `fromKeyboard`, positioned at the card, and the menu then focuses its first item; the contextmenu event Chromium sends after the Menu key (`button === -1`) is ignored. Closing Zoom returns focus to the clip it showed,
8. zoom is clip-centric at the app level but the overlay stays media-source-oriented; a right-click on it opens Zoom's edit menu, a backdrop click is reported as `closeRequested` rather than closing it, and it hosts Zoom edit mode's surface (see [Zoom Edit Mode](#zoom-edit-mode)). It shows the zoomed clip's name along the bottom of the frame, over the edit player too, hidden with the grid's titles (`setTitleHidden`),
9. rename: the grid's right-click menu on a clip starts with Rename, and F2 on a focused card does the same; [`ClipNameEditor`](../../src/ui/clip-name-editor.ts) turns the card's name into a field holding the name without its extension and the grid reports `renameRequested({ clipId, newFilename })`. [`ClipRenameWorkflow`](../../src/app/clip-rename-workflow.ts) asks the main process through `IClipRenameService` ([`ElectronClipRenameService`](../../src/adapters/electron/electron-clip-rename-service.ts), `clip-sandbox:rename-clip`), shows a refusal in the card (`showRenameProblem`), and after a rename updates every view and saved collection through `ClipFileReplacement.rename`, the path Replace uses, which also reports collections it could not rewrite. In the main process [`ClipFileRenamer`](../../electron/clip-file-renamer.cjs) checks the folder grant and file name through `GrantedClipResolver`, refuses a name Windows cannot create (`ClipFilenameRule.isCreatableVideoFilename`), a changed extension or a name another file has (a change of case alone is allowed), then renames and answers the new folder entry,
10. the toolbar activity indicator replaces the old footer toast and is now the shared surface for load/save/delete/edit messages,
11. fullscreen is coordinated by `CollectionFullScreenWorkflow`, using grid layout rules plus fullscreen adapters,
12. every dialog's control attaches [`ButtonRowArrowKeys`](../../src/ui/button-row-arrow-keys.ts) to its root, so Left and Right move the focus between the buttons next to the focused one, wrapping; keys typed in a field stay with the field.

## Risky Seams

1. [`src/app/app-controller.ts`](../../src/app/app-controller.ts) is the single place that knows both controls and workflows. Construction order matters: workflows must subscribe before `ApplicationShellControl.start()` emits the first `screenChanged`. Workflows that call each other (for example the folder reload used by refresh) are connected here, and keeping that set small keeps the flows independently testable.
2. [`src/ui/clip-collection-grid-control.ts`](../../src/ui/clip-collection-grid-control.ts) owns DOM rendering, selection, drag/drop, and media-element sources. Changes can affect both UI behavior and lifecycle cleanup.
3. [`electron/preload.cjs`](../../electron/preload.cjs) and [`electron/main.cjs`](../../electron/main.cjs) define the desktop trust boundary. Over-broad IPC or preload exposure is the main architecture risk in this runtime.
4. [`src/app/collection-full-screen-workflow.ts`](../../src/app/collection-full-screen-workflow.ts) owns fullscreen timers and input while the grid owns cancelable media rotation. Exit, view replacement and disposal must cancel pending ended listeners.
5. The current view contract is intentionally split: `Pipeline` and `Collection` are durable models, while `PipelineWorkingCopy` owns the active mutable `ClipSequence` working copy. Changes here can silently break dirty-state tracking, save enablement, and delete semantics.
6. The TypeScript migration now has strict authored-source coverage enforced by `npm run typecheck` through [`tsconfig.strict-src.json`](../../tsconfig.strict-src.json). Authored TypeScript under `src/` should not use `// @ts-nocheck`; the remaining unchecked runtime bridge is the CommonJS Electron shell under [`electron/`](../../electron/), which is intentionally outside this strict source config for now.
7. One `FrameReviewPlayerControl` moves between GIF Extraction, Refine Gif and Zoom edit mode. While the mode is active its session decides what the player shows, so every way out of Collection (screen change, folder load, collection switch) must end the mode first: `ZoomEditModeLeavePolicy`, `FolderSelectionWorkflow` and `OpenFolderRefresher` all read `ActiveZoomEdit`. A new way to leave Collection, or a new screen that attaches the player, needs the same check.

### Shell remediation verification (2026-09-09)

[`IShortcutDescriptor`](../../src/app/shortcut-descriptor.ts) represents optional explicit groups and alternative complete key sequences; each sequence is a chord. [`KeyboardMapControl`](../../src/ui/keyboard-map-control.ts) renders these as static keycaps, while KeyboardMapControl owns its Close button and requests dismissal through [`GlobalUtilityCoordinator`](../../src/ui/global-utility-coordinator.ts). Activity owns visible status text, accessible name and unresolved counts; errors override ongoing status, and an operation failure ends its progress state. The shell uses local inline icons and existing CSS/controller ownership without a new dependency. See the [remediation verification](../research/application-shell-ux-remediation-verification.md) for current visual evidence and manual-QA boundaries.

### Shell component boundaries (ownership correction)

`CollectionScreen` coordinates initial focus through `focusSelectedClip()` on the grid and `focusBrowse()` on the toolbar. It does not query child markup or calculate grid padding. `ClipCollectionGridControl` owns selected-card focus and reads its allocated container height minus current vertical padding. Its existing optional height provider remains available to standalone callers.

`FoldablePanelControl.targetWidth` owns the interpretation of panel state and sizing CSS; the shell sums those public measurements. Screen roots, command surfaces, utility panels and triggers are explicit mounting/visibility contracts, not permission to inspect descendants. Keyboard and Activity controls handle their own Close buttons and call injected close requests. The coordinator handles exclusivity, outer-surface visibility, placement and focus return. Fullscreen button rendering belongs to `MainToolbarControl`; the fullscreen session reports state through an injected callback. Activity auto-open asks Zoom, Save and Conflict controllers about their state; the remaining generic open-dialog query detects the browser dialog surface rather than a component's private selectors.


### Encapsulation corrections (2026-09-10)

Grid ownership includes normal/fullscreen DOM layout, visibility buffers and rotation completion. `rotateVisibleClip()` switches intact cards using visibility and CSS order; sources, metadata callbacks and canonical IDs stay together, and the outgoing visual slot is retained. `cancelRotation()` removes the pending listener and restores looping; restore/render/invalidation/disposal invoke it. `fsApplySlots(slots)` receives a value instead of a shared state bag. The composition root no longer obtains grid descendants for layout; `DomRendererAdapter` and the raw grid getter were removed. Pure grid calculations remain injectable, as does standalone height allocation.

The grid's implementation fields/helpers, dialog/menu fields, metadata tracker state, Zoom DOM and adapter dependencies are private. Public callbacks carry semantic selection/point data, not cards. Explicit outer mounting/visibility surfaces remain legitimate contracts. These are TypeScript encapsulation boundaries, not a security sandbox against arbitrary JavaScript reflection.

`PipelineWorkingCopy.hasDirtyClipSequenceChanges` compares the current sequence to the saved collection or pipeline every read; mutation through a shared sequence cannot leave a stale flag. Canonical mutable Clip identities remain shared deliberately. `Clip` and `Pipeline` hold frozen `ClipSource` values and reject anything else at run time, so outside code cannot change or split a clip's source. A saved clip becomes a `ClipSource` through `ElectronFolderService.clipSourceOf` before `CreatedClipInsertion` or `ClipFileReplacement` shows it. Desktop-path edit contracts remain an explicit Windows-first tradeoff, rather than an implicit private-state dependency.

Acceptance and remaining scope: [encapsulation correction verification](../research/encapsulation-fixes-verification.md). The historical review is a before-state inventory, not a current list of open defects.


### Edit callback recovery (2026-09-10; runner removed 2026-10-30)

The one-shot edit runner this section described was removed with Loopify's move into Zoom edit mode (2026-10-30); a saved clip the views cannot show is reported by `EditedClipSaveWorkflow`. Zoom now reports active-video playback failures through its `playbackFailed` event (`{ clipId, name, error }`), which `ZoomWorkflow` reports. Zoom owns attempt generations and deduplication; closed/replaced/superseded attempts and rejections after a playing event are ignored. The app presents Activity recovery guidance and records native error details. Background grid diagnostics retain their existing behavior.
