## Purpose

Clip Sandbox is a local Electron desktop app for reviewing video clips from one selected folder at a time. The durable model is a `Pipeline`: a folder-backed container of all clips plus zero or more saved collections. The user can browse the full pipeline, switch to a saved collection, reorder clips, save or save-as-new, add to another collection, move clips to the Recycle Bin, zoom a clip, run the built-in `Loopify` edit from zoom mode, and enter fullscreen review mode.

The renderer is still framework-free. The main architectural change from the OO/TypeScript refactor is that authored renderer code now lives in `src/**/*.ts`, the Electron shell remains pragmatic CommonJS, the adapter layer under `src/adapters/` is now class-backed, and `index.html` loads emitted runtime JavaScript from `build/src/...`.

## Stable Concepts

1. `Clip` in [`src/domain/clip.ts`](../../src/domain/clip.ts): canonical runtime clip object with generated id, its [`ClipSource`](../../src/domain/clip-source.ts) (an immutable value: file name, the media address the grid and Zoom play, and the desktop path when there is one, built only through `ClipSource.create`), duration, intrinsic video dimensions, and metadata failure state. The domain uses no DOM type; its tests run in Node.
2. `ClipSequence` in [`src/domain/clip-sequence.ts`](../../src/domain/clip-sequence.ts): mutable runtime ordered clip list used by the grid, selection, reorder, and transient view state.
3. `Collection` in [`src/domain/collection.ts`](../../src/domain/collection.ts): durable ordered subset of pipeline clip names, optionally backed by a `.txt` file, with collection-specific append/remove/materialization behavior.
4. `Pipeline` in [`src/domain/pipeline.ts`](../../src/domain/pipeline.ts): folder-backed container of one `ClipSource` per available video plus zero or more saved `Collection` objects. It owns one canonical runtime `Clip` per active-session video file, explicit `materializePipeline(...)` / `materializeCollection(...)` flows, and in-memory collection/video mutation rules such as `addClipsToCollection(...)` and `removeVideos(...)`.
5. `PipelineWorkingCopy` in [`src/app/pipeline-working-copy.ts`](../../src/app/pipeline-working-copy.ts): active loaded-pipeline working state. It owns generated clip ids, the selected pipeline/collection sequence, derived dirty-state comparison (never a cached flag), active clip resolution, reorder/remove mutation, and created-clip insertion while keeping the durable `Pipeline` focused on folder contents and saved collections.
6. `AppSessionState` in [`src/app/app-session-state.ts`](../../src/app/app-session-state.ts): class-backed app-shell state holding the open folder's `FolderAccess`. The pending selection action waiting on the unsaved-changes prompt belongs to `FolderSelectionWorkflow`. It does not own loaded pipeline selection state.
7. `CollectionFullScreenWorkflow` in [`src/app/collection-full-screen-workflow.ts`](../../src/app/collection-full-screen-workflow.ts): Collection-only full screen coordinator for slot input, title hiding and rotation scheduling. It passes slot values and rotation requests to the grid; it receives no card/video handles. [`FullscreenAdapter`](../../src/adapters/browser/fullscreen-adapter.ts) distinguishes the document-root Collection element from the GIF player's element while retaining an app-wide any-full-screen check.
8. [`FolderAccess`](../../src/app/folder-access.ts) (held as `folderAccess`, `null` when no folder is open): access to the opened desktop folder, backed by its absolute path. Only [`ElectronFolderService`](../../src/adapters/electron/electron-folder-service.ts) creates one, checking the path where it arrives from the desktop API, so callers need only a null check. [`FolderAccessRegistry`](../../electron/folder-access-registry.cjs) records picker-selected paths and explicitly opened catalog pipelines as per-window folder grants; listing or expanding the catalog grants only opaque read access to its entries. Only a granted folder can be written, appended to, have files moved to the Recycle Bin, or be re-enumerated through Electron IPC.
9. `clipSandboxDesktop` in [`electron/preload.cjs`](../../electron/preload.cjs): preload-exposed desktop API used by the renderer-facing Electron services.
10. `ClipEditor` in [`src/business-logic/clip-editor.ts`](../../src/business-logic/clip-editor.ts): edit request executor that validates requests, derives preferred output filenames, and delegates execution to the runtime editing service.
11. `ZoomVideoEditWorkflow` in [`src/app/zoom-video-edit-workflow.ts`](../../src/app/zoom-video-edit-workflow.ts): app-layer workflow boundary that runs `ClipEditor` for a supplied zoom source clip and emits edit lifecycle callbacks without knowing pipeline, grid, toolbar, or zoom overlay details.
12. [`ActivityLogger`](../../src/app/activity-logger.ts) owns the session activity contract, progress/success/error state, retained history, and change subscriptions. [`ActivityIndicatorControl`](../../src/ui/activity-indicator-control.ts) subscribes and renders the global status surface, detailed errors, and local interactions.
13. `video edit runtime` in [`electron/video-edit-runtime.cjs`](../../electron/video-edit-runtime.cjs): trusted-process runner that resolves `ffmpeg`, collision-checks the output path, creates the derived file, and returns folder-entry metadata.
14. `frame-review native toolchain` in [`native/frame-review/`](../../native/frame-review/) and [`tools/frame-review/`](../../tools/frame-review/): explicit Windows x64 build-time ownership for the selected LibVLC playback service, BestSource exact-frame service, bounded binary protocol, diagnostic helpers, and one pinned x264-enabled FFmpeg/FFprobe distribution. Normal build/startup never bootstraps or compiles it.
15. `FrameReviewHost` in [`src/frame-review/host/frame-review-host.ts`](../../src/frame-review/host/frame-review-host.ts): trusted per-window owner of opaque source handles and review sessions. `ReviewSession` coordinates provisional LibVLC playback, asynchronous prepared-review activation, exact BestSource access, source-generation invalidation, bounded scrub/held-step workloads, and idempotent disposal. Playback commands and proxy activation are serialized so a Play after Pause cannot be overwritten by a concurrent proxy open. It owns live-clock relative playback jumps and elapsed-time lookup of exact scrub frames. The renderer reaches it only through [`electron/frame-review-ipc.cjs`](../../electron/frame-review-ipc.cjs) and [`ElectronFrameReviewService`](../../src/adapters/electron/electron-frame-review-service.ts); source, index, proxy, and cache paths never appear in that renderer service contract.
16. `FrameReviewPlayerControl` in [`src/ui/frame-review-player-control.ts`](../../src/ui/frame-review-player-control.ts): the single renderer-owned movie viewport, transport, readiness presentation, progress bar, and GIF movie full screen owner shared by GIF Extraction and both Refine contexts. The player element alone enters full screen after exact readiness; the existing seek row appears temporarily, and `fullscreenchange` reconciles focus and presentation without a shell screen change. Movie playback runs at the native player's default 1× speed; progress seeking and exact-frame scrubbing remain separate commands. It owns the transient jump duration, last manual scrub direction, bounded pending jump time, and interruption order; [`GifWorkflowKeyboard`](../../src/ui/gif-workflow-keyboard.ts) maps physical top-row digit shortcuts to the same command as the Jump button and routes `F`/`Escape` for movie full screen. Attaching a new review session resets the timeline, displayed time, and scrub direction before new frames arrive; if the player was full screen, new-frame painting waits for normal presentation. It renders capture identity from the newest displayed frame synchronously and never owns or disposes the leased review session.
17. The GIF sessions: [`GifExtractionSession`](../../src/app/gif-extraction-session.ts) serves GIF Extraction (opens a movie by picker, marks and locks ranges) and [`CollectionClipRefinementSession`](../../src/app/collection-clip-refinement-session.ts) serves Collection Refine (opens a clip's original movie and imports its one range). Both extend [`MovieRangeSession`](../../src/app/movie-range-session.ts), which builds their parts and assembles the one snapshot both GIF screens and the Clips panel read:
   - [`GifSessionStatus`](../../src/app/gif-session-status.ts): the status line and preview revision; the single trigger for publishing;
   - [`CurrentMovie`](../../src/app/current-movie.ts): choosing, opening and following the movie under review, its source generation, preparation and readiness reporting; it reports `exactCaptureReady` and `reviewEnded` as events, and the session drives a change of movie;
   - [`CaptureQueue`](../../src/app/capture-queue.ts): the draft and locked ranges, their thumbnails, the saved-frame checks (run by locking and refining themselves), removal and restoring saved captures; it saves through [`SavedCaptureStorage` or `UnsavedCaptureStorage`](../../src/app/capture-storage.ts), which the composition root chooses;
   - [`RangeExtraction`](../../src/app/range-extraction.ts): extraction runs, their Activity reporting and destination;
   - [`RangeRefinement`](../../src/app/range-refinement.ts): starting, abandoning and committing a refinement.
   
   No session has a mode. [`SavedCaptureQueuePersistence`](../../src/app/saved-capture-queue-persistence.ts) owns each source generation's durable queue binding and stale-range marks.
18. `ClipExtractionWorkflow` in [`src/app/clip-extraction-workflow.ts`](../../src/app/clip-extraction-workflow.ts): exact-only single/batch orchestration owner. It preserves per-range outcomes, continues after individual failures, cancels active work, and retries a failed collection publication without re-encoding completed media.
19. `ApplicationShutdownCoordinator` in [`src/app/application-shutdown-coordinator.ts`](../../src/app/application-shutdown-coordinator.ts): idempotent renderer teardown owner. It stops new screen/keyboard/resize actions synchronously, begins GIF workflow disposal, and destroys remaining controls only after that disposal settles.
20. `AppSettings` in [`src/app/app-settings.ts`](../../src/app/app-settings.ts) and [`AppSettingsService`](../../src/app/app-settings-service.ts): persisted renderer preferences, including `startupScreenId`, its default/fallback (`gif-extraction`), and committed immutable settings state. The service owns load/save; it does not own the active screen.

The important split remains durable selection state vs runtime working copy:

1. runtime UI works with `Clip` and `ClipSequence`,
2. active loaded-folder selection state works through `PipelineWorkingCopy`,
3. durable selection and persistence work with `Pipeline`, `Collection`, and explicit pipeline-mode vs active-collection branching,
4. `Collection` remains filename-based durably, while materialized collection sequences reference canonical `Clip` instances from the active `Pipeline`.

## Architecture Axioms

These are normative defaults for future work. Do not violate them without a concrete reason and user approval. UI design follows [`ui-coding-quality.md`](../../ui-coding-quality.md); axioms 2, 3, 7 and 11 record how this repository applies it. Only the composition root (`app-controller.ts`) imports from `src/ui/`; types both layers use, such as [`IShortcutDescriptor`](../../src/app/shortcut-descriptor.ts) and [`IFrameReviewDisplayedCapture`](../../src/app/frame-review-displayed-capture.ts), live in `src/app/`.

1. Keep the renderer framework-free unless a larger architecture decision is approved.
2. Keep [`AppController`](../../src/app/app-controller.ts) as the composition root only: it constructs services, controls, screens and workflow classes, connects them, and starts the application. User flows live in workflow classes under [`src/app/`](../../src/app/) (`*-workflow.ts`); do not put flow logic, domain rules or reusable UI internals in `AppController`.
3. Controls report user intent as typed events (`EventSource` in [`src/app/event-source.ts`](../../src/app/event-source.ts)) that workflows subscribe to; workflows depend on narrow consumer-declared `I…` interfaces and never import from `src/ui/`. A reply to a single request, such as a dialog's submit result or a menu item callback, stays a call argument. Questions other parts ask ("may this screen be left?", "is this name new?") are answered by standalone query components, not workflows. There is no startup check that every event has a subscriber; an unhandled event shows up as a control that does nothing, which the app-level and end-to-end tests are expected to catch.
4. Keep durable pipeline and collection state in domain models plus explicit active-collection selection state, not in DOM order or DOM-selected state.
5. Prefer explicit pipeline-vs-collection flows when their semantics differ materially. Do not introduce shared protocol layers or generic source ids unless they are buying real simplification.
6. Keep Electron main/preload and local filesystem behavior behind adapters or services. Do not leak raw Electron or Node APIs broadly into renderer code.
7. Keep reusable UI behavior in focused controls (`…Control`) and screens under [`src/ui/`](../../src/ui/); `AppController` only builds and connects them.
8. Default production TypeScript behavior to explicit class ownership, including deterministic calculations and text formatting. Treat every module-level function as a design smell that requires an ownership decision; document any intentional exception.
9. Treat [`docs/documentation/object-oriented-exception-register.md`](../../docs/documentation/object-oriented-exception-register.md) as the reviewable record of intentionally non-OO holdouts.
10. Treat `docs/agent-docs/` as the canonical agent-facing architecture knowledge base. Historical specs and plans are not canonical onboarding material.
11. A UI control owns binding and unbinding events originating from its own elements. [`ApplicationEventController`](../../src/app/application-event-controller.ts) is limited to application-wide document/window events. A control that closes or repositions on interaction outside itself (the order menu, context menu and utility panel) may listen on its own element's document and window, and removes those listeners in `destroy()`. A control also finds or creates its own parts and owns its display text: `AppController` passes the document or a root plus behavior (validators, `AppText`, callbacks), never a control's inner elements, attributes or labels. Controls built from the page expose a factory for this, such as `fromDocument`, `forClipMenu`, `forCollectionRefinement`, `RefineGifScreen.forGifExtraction` or `ApplicationShellControl.sidePanelsIn`, using [`DocumentElements`](../../src/ui/document-elements.ts) for required and optional lookups.
12. Inject shared service-like objects such as [`AppText`](../../src/app/app-text.ts) rather than importing static namespaces or free formatting functions.
13. Prefix authored TypeScript interface names with `I`; classes and type aliases retain responsibility-based names without a type-kind prefix.

## Core Runtime Flows

### Native Frame-Review Runtime Boundary

The production-owned native sources are the selected software-only implementation carried from the exact-frame spike: LibVLC owns clocked playback/audio, while BestSource owns indexed canonical frame identity and exact access. The versioned `FVSP` protocol rejects unsupported versions and bounded-length violations before payload allocation. The x264-enabled FFmpeg 9 build supplies `ffmpeg.exe`, `ffprobe.exe`, native libraries, current AAC handling, and `libx264rgb` from one vcpkg dependency graph; QSV, oneVPL, CUDA/NVENC, AMF, and nonfree features are excluded. [`NativeProductLocator`](../../electron/native-product-locator.cjs) is the single development/packaged-layout resolver for frame review, GIF Extraction, and Loopify; it also supplies the staged runtime-library environment required by FFmpeg and FFprobe. No legacy `@ffmpeg-installer/ffmpeg` fallback remains.

Run `npm run frame-review:bootstrap`, `npm run frame-review:build`, and `npm run frame-review:test` explicitly. Bootstrap verifies pins and reuses valid dependencies; a clean BestSource bootstrap explicitly fetches pinned Ninja through vcpkg before locating its executable, since dependency installation alone need not populate that tool. CMake owns incremental helper/test targets. `npm run build` and `npm start` do not install dependencies or compile native tools. When the production binaries are already present, Electron composes a `FrameReviewHost` for each window and registers the narrow preload API; missing native products do not prevent the existing Collection/Settings shell from starting, but opening frame review will fail explicitly.

Movie opening has three progressive capabilities. Dedicated frame-review movie selection registers the original source with the window's `FrameReviewHost` and returns an opaque handle; ordinary pipeline folder entries and `ClipSource` values do not retain that session capability. LibVLC opens the selected original source first for provisional playback with audio. `ReviewPreparationService` then inspects the source and validates a content- and tool-version-bound cache identity. On a cold miss it conditionally normalizes timestamps and creates/publishes the software GOP1 review proxy first; `ReviewSession` switches LibVLC to that proxy as soon as it is usable, so timestamp scrubbing no longer waits for exact-frame work. It then builds the canonical BestSource index, indexes the proxy, validates the ordinal frame map, and publishes the complete prepared review. Exact capture remains disabled until that final prepared review is activated. Indexing emits real native progress when the gate supplies totals; other phases are deliberately indeterminate. After exact readiness, frame-scrub delivery carries canonical identity and pixels together; capture during clocked playback remains a timestamp/inexact point.

`PlaybackProxyCache` owns early proxy publication and one process-wide writer per identity; its immutable proxy and optional normalized source live under `<app-folder>/playback-proxy-cache`. `ExactReviewProxyCache` retains atomic publication for the same proxy together with its exact-review set: canonical indexes live under `<app-folder>/frame-index-cache`, while proxy indexes, frame maps, hard-linked proxy/normalized media, and manifests live under `<app-folder>/exact-review-proxy-cache`. Each requesting session is an independent consumer: cancelling one consumer does not cancel a writer still needed by another, while abandoning the final consumer aborts the writer and removes its partial workspace. The application folder is the project directory in development (the Electron profile folder when `CLIP_SANDBOX_E2E=1`, so each end-to-end test starts with empty caches and deletes them with its profile) and the installed executable's containing directory in a packaged build, never an `app.asar` path. Valid full-review hits skip both builders and preserve mtimes across session and process restarts. Temporary partial entries are ignored and cleaned, stale or incomplete entries rebuild, and ordinary session/app shutdown never deletes validated cache assets.

An optional `loop-timeline-v1.json` sidecar beside each prepared proxy manifest stores indexed proxy PTS by ordinal for exact capture preview. [`ProxyFrameTimelineCache`](../../src/frame-review/host/proxy-frame-timeline-cache.ts) validates or regenerates it from the finished proxy index; failure leaves ordinary proxy playback and exact scrub available. [`ReviewSession`](../../src/frame-review/host/review-session.ts) owns the A–B lifetime, ordinal-to-player-time lookup, Space handoff, and reset recovery; the shared [`FrameReviewPlayerControl`](../../src/ui/frame-review-player-control.ts) displays the resulting playback and exact frames. The GIF screens expose A/S exact jumps, Z loop preview, Space pause/resume, and X lock/commit for the active exact draft, selected locked range, or staged Refine pair. A–B picture-boundary misses remain provisionally accepted pending the user's real-clip review; the pinned proxy profile uses zero-origin indexed PTS converted through its rational timebase; the host rejects unsupported nonzero origins. The native service interpolates LibVLC timer points between callbacks, including across loop seeks, for the Space handoff. CFR, VFR, and actual timestamp-normalized coded fixtures exercised this mapping, while final full-suite and user real-clip checks remain in the plan. See the [execution plan](../plans/capture-preview-and-shortcuts-exec-plan.md).

### Native Desktop Frame

### Application Shell and Screen Ownership

`index.html` defines the global app bar, central command host and main screen host. [`ApplicationShellControl`](../../src/ui/application-shell-control.ts) owns a nonempty set of [`IAppScreen`](../../src/ui/app-screen.ts) registrations, the persistent workspace selector, active content/commands and delegated initial focus. Screen roots stay mounted but inactive roots are hidden/inert; inactive commands are detached. Activation is synchronous, so there are no queued stale completion callbacks. The selector is hidden for a single registration and lives in the global app bar, not in the movie/media workspace. The shell may receive an explicit initial screen id, but it has no screen-id branches or Electron/filesystem dependencies.

Production registers [`CollectionScreen`](../../src/ui/collection-screen.ts), [`GifExtractionScreen`](../../src/ui/gif-extraction-screen.ts), contextual [`RefineGifScreen`](../../src/ui/refine-gif-screen.ts), and [`SettingsScreen`](../../src/ui/settings-screen.ts). Fixed screens receive persistent selector entries; a contextual screen receives a temporary truthful entry only while active. Collection adapts the existing Collection DOM, owns initial focus and supplies the grid's allocated content height. `MainToolbarControl` remains the Collection command-state renderer; its name and stable element ids are retained. Existing Activity and the prominent Workspace selector live in the global bar, while movie controls, zoom/context overlays and screen-specific commands remain in their own workspace areas. Settings has no command bar and exposes the persisted Startup workspace preference. The Pipelines catalog uses a persistent fallback host inside the shell panel mount, so screen activation preserves its tree and disclosure state. The shell delivers document key presses to the active screen's `onKeyDown` hook. `CollectionScreen` reports them as `keyPressed`, which `AppKeyDownHandler` handles (Collection shortcuts first, then Collection full-screen keys, but never keys typed into an open dialog or an editable field, and nothing while a global utility is open). Keys pressed on a focused clip card (arrows, Space, Alt+Arrow, Shift+F10, Menu) reach the grid only through that handler's `grid.handleCardKey`, so its guards also keep them out of Zoom and Collection full screen; Enter/Z open the focused or selected clip and Ctrl+S calls `CollectionSaveWorkflow.saveActive`; the GIF screens pass them to their shared keyboard handler, [`GifWorkflowKeyboard`](../../src/ui/gif-workflow-keyboard.ts) is activated and released by the two GIF screen lifecycles.

[`AppSettingsService`](../../src/app/app-settings-service.ts) owns the committed immutable [`IAppSettings`](../../src/app/app-settings.ts) value: an optional Pipelines root, the default audio preference for new single-clip playback (off initially), and the persisted `startupScreenId` preference (GIF Extraction by default); `whenLoaded()` settles after its first load attempt, and `FolderSelectionWorkflow` waits on it before loading a folder. [`SettingsScreen`](../../src/ui/settings-screen.ts) only shows the values and busy state and reports `folderChooseRequested` and `preferenceChangeRequested`; [`SettingsWorkflow`](../../src/app/settings-workflow.ts) loads, saves, chooses the root, reports to Activity, reloads the Pipelines catalog after load or a root change, and opens the saved startup screen unless the user has already moved. The [`Electron adapter`](../../src/adapters/electron/electron-app-settings-service.ts) validates unknown IPC responses and the domain parser owns valid startup-workspace membership. [`AppSettingsStore`](../../electron/app-settings-store.cjs) reads and atomically writes versionless known fields in `app-settings.json` beneath Electron userData. It ignores unrecognized persisted fields and returns an Activity-visible diagnostic; invalid or unreadable known settings fall back to defaults. Failed writes preserve the committed value. Native folder cancellation saves nothing. The shell is constructed passive; `start()` performs its first activation after every workflow has subscribed to its `screenChanged` event, so no event fires before wiring is complete; `ApplicationShellControl` owns the active screen after that handoff, not the persisted preference. After settings load, [`PipelineCatalogRuntime`](../../electron/pipeline-catalog-runtime.cjs) reads only immediate child folders of the configured root, keeps folders containing at least one recognized top-level video, and returns opaque per-window catalog ids and names; `extraction-tmp` sorts first and the remaining names sort naturally. [`PipelineCatalogControl`](../../src/ui/pipeline-catalog-control.ts) owns the side-panel disclosure tree: expanding a pipeline lazily reveals distinct Collections and Clips groups, and expanding a collection reveals its listed clip names. Load is a separate action that obtains the opened folder's `FolderAccess` through the catalog grant; it uses the same unsaved-collection guard as Browse Folder, while catalog discovery never mutates the active `PipelineWorkingCopy`. Changing the root reloads this temporary filesystem catalog; a future durable pipeline registry may replace its provider without changing the panel contract. The trusted extraction runtime also reads the root only to resolve the fixed `extraction-tmp` system pipeline. Zoom samples the audio preference for each new video; its local toggle stays local and the grid remains muted. See [`pipeline-catalog-runtime.spec.ts`](../../tests/unit/pipeline-catalog-runtime.spec.ts), [`pipeline-catalog-control.spec.ts`](../../tests/unit/pipeline-catalog-control.spec.ts), and [`settings.spec.ts`](../../tests/e2e/settings.spec.ts) for coverage.


[`FoldablePanelControl`](../../src/ui/foldable-panel-control.ts) owns each panel's folded state, ARIA/inert state, focus transfer, and transition completion. Its generation token rejects stale completions after reversal. `IAppScreen.panelContributions` supplies mountable content objects by panel id without shell knowledge of screen ids or access to control-owned DOM; captured ranges mount only for contributing GIF screens. `IAppScreen.initiallyFoldedPanelIds` names the panels folded on a screen's first entry; all others open. The shell normally restores each screen's last panel state on return. `IAppScreen.openPanelIdsOnEntry` overrides that saved state for panels a screen needs open whenever it is entered; Refine Gif uses it for Clips, while users may still fold Clips during that visit. CSS owns 240px/36px panel widths and 240/280ms closing/opening timing; reduced motion completes immediately. The shell measures destination central width and wrapped command height once, calls the active screen's `onBoundsChanging(width, durationMs)` hook, and calls its `onBoundsSettled()` hook once after all moving panels finish. The GIF capture queue belongs to the GIF sessions' `CaptureQueue`, not to this shell mechanism.

`AppController` composes these controls. `CollectionScreen` forwards the shell's bounds hooks to its grid, and the grid observes its own root, skipping relayout while a Collection workspace resize is in progress. `CollectionFullScreenWorkflow` and `AppKeyDownHandler` receive the grid, Zoom and full-screen adapter themselves behind narrow interfaces; `CollectionFullScreenWorkflow` asks the shell to hide the window's shared parts (`setFullScreenLayout`) rather than touching the page. GIF Extraction and Refine Gif reparent one physical `FrameReviewPlayerControl` between their player hosts; they do not reconstruct it, create a second playback engine, or add a second timeline. The player keeps ordinary playback/time seeking usable before exact preparation, switches the sole progress bar to canonical ordinals when ready, and routes held arrows through the session's bounded adjacent-step scheduler. Its movie full screen uses the player root, preserves that host's normal height while lifted, and exits before painting a different review session; it does not activate a new shell screen. [`ClipCollectionGridControl`](../../src/ui/clip-collection-grid-control.ts) opts into `coordinateWorkspaceLayout` in production: `beginWorkspaceResize` calculates the destination once and interpolates existing cards' positions/sizes; `endWorkspaceResize` reconciles actual bounds. Grid metric/current-column bookkeeping remains inside the grid controller. Normal allocated width excludes root padding; the original CSS-grid renderer remains available for other callers and Collection full screen. Collection full screen clears positioned card geometry and hides both panels, then restores their prior states on exit. App-wide utility closure and Activity auto-open suppression still apply to either full screen element. Tests: `foldable-panel-control.spec.ts`, `application-shell-control.spec.ts`, player/keyboard unit tests, grid integration tests, [`gif-movie-fullscreen.spec.ts`](../../tests/e2e/gif-movie-fullscreen.spec.ts), and [`gif-extraction-shell.spec.ts`](../../tests/e2e/gif-extraction-shell.spec.ts). Electron scenarios run with one Playwright worker because native windows share desktop focus and pointer state.

[`CurrentMovie`](../../src/app/current-movie.ts) owns one selected movie, its frame-review session and a source generation; [`CaptureQueue`](../../src/app/capture-queue.ts) owns the in-memory capture queue. [`CaptureThumbnails`](../../src/app/capture-thumbnails.ts) owns the draft/range thumbnail slots and their asynchronous cache-resource lifetime; `CaptureQueue` decides when workflow events replace, commit, refine, remove, or clear them. `RangeCaptureModel` implements the lock-only `Q`/`W`/`X` workflow: marks replace draft endpoints until `X`, `W` cannot modify a locked range, and the next `Q` begins a new draft. Endpoint values distinguish canonical exact frames from playback timestamps; either timestamp makes a locked range require refinement. Capture reads the same frame already displayed by `FrameReviewPlayerControl`, so playback marking does not pause while exact progress-bar scrubbing rejects late playback frames. Source replacement saves the draft with its movie and does not dispose the old review or thumbnails until the candidate opens; `MovieRangeSession.replaceSource` owns that order. During candidate opening, old captures remain visible but capture, refinement, and extraction are unavailable. Failed or cancelled opening leaves the old session intact; successful opening attaches the new review, resets the player timeline, then restores that movie's captures.

The active draft and locked unfinished captures are written as per-movie records under Electron `userData/clip-captures` by [`SavedCaptureCodec`](../../src/app/saved-capture-codec.ts), which owns the stored record format (its `exact-frame` endpoint kind is also checked by the desktop store) and restores a [`RangeCaptureModel`](../../src/domain/range-capture-model.ts) through `RangeCaptureModel.restore`; the domain model holds no storage format. A refused capture step returns a code from the domain (`RangeCaptureRejection`); [`CaptureRejectionText`](../../src/app/capture-rejection-text.ts) turns it into the status line, naming the key from `GIF_CAPTURE_KEYS` in [`gif-workflow-keyboard.ts`](../../src/ui/gif-workflow-keyboard.ts), which the composition root passes in. [`SavedCaptureQueuePersistence`](../../src/app/saved-capture-queue-persistence.ts) binds one source generation to its opaque movie reference, deduplicates asynchronous saves, tracks ranges whose saved frames no longer matched the movie when checked (stale ranges), and rejects late attach results after a movie switch invalidates that binding. `CaptureQueue` owns the live `RangeCaptureModel` and saves at queue transitions through its capture storage: `SavedCaptureStorage` wraps the binding, while Collection Refine uses `UnsavedCaptureStorage`. [`SourceFingerprint`](../../src/frame-review/model/source-fingerprint.ts) selects a queue from the native sampler's content digest, size, duration, stream and profile fields, without the cache build versions or source path. [`ClipCapturesStore`](../../electron/clip-captures-store.cjs) owns atomic bounded JSON, per-movie coalesced writes and reads ordered after pending writes; [`ClipCapturesIpcBoundary`](../../electron/clip-captures-ipc.cjs) keeps saved paths in main and grants the renderer only opaque movie references for an explicitly opened source. `AppController` wraps the renderer-facing [`ElectronClipCapturesStoreService`](../../src/adapters/electron/electron-clip-captures-store-service.ts) in `SavedCaptureStorage` and gives it to `GifExtractionSession`. The sessions also receive the `ActivityReporter`, the Activity log and diagnostics for its reporting, and two awaited collaborators behind narrow interfaces: a publication listener (`OpenFolderRefresher`, so extraction continues only after the open folder has reacted) and capture positioning (the shared player, whose failure the session reports). Startup leaves the movie session empty. Start/End marks and locked ranges save asynchronously and restore on matching content when the user explicitly opens that movie, including after restart. When saved captures exist, GIF Extraction displays the exact frame after the last saved range end or the latest unfinished draft endpoint, clamping at the final frame. Exact saved endpoints contain ordinal, decoded-frame hash and review time; saved draft endpoints are checked by Lock itself, and locked endpoints by Refine and Extract themselves, so no caller runs the check; they use BestSource's metadata-only `identity` command without seeking playback. The separate `thumbnail` command redraws saved start frames without changing the player's or adjacent-step cursor. Extraction status and thumbnail resources remain session-only; fully published ranges leave the durable unfinished queue.

[`RangeRefinementDraft`](../../src/app/range-refinement-draft.ts) is a one-range staging object owned by [`RangeRefinement`](../../src/app/range-refinement.ts). It preserves an inexact or exact captured range, focuses one endpoint at a time (Start first on entry), and accepts only exact displayed captures from the current source generation. The Clips panel keeps the complete queue visible and offers Refine and double-click entry for every captured range. Choosing another range replaces the active refinement immediately, discarding only its staged endpoints without a prompt; the underlying captured range remains unchanged until Lock. Start/End cards jump to their stored endpoints; Q/W stage the currently displayed exact frame. `X` atomically replaces the same opaque queue entry only when both exact ordinals form a valid inclusive range; Back abandons staging without changing the queue. An unchanged exact lock preserves its extraction outcome. A changed lock resets that range's extraction outcome to pending; earlier published media remain saved, and extraction is again an explicit action. Active extraction and unresolved collection publication block changed locks until completion or retry. Source replacement or range removal invalidates an active refinement. The contextual Refine Gif screen enters exact scrub near the stored endpoint through the shared player and restores queue focus on return. `E` extracts the committed current exact range; `Extract All` snapshots all currently eligible exact ranges and continues after individual failures. Editing an existing saved clip without its source movie is a separate future Edit flow.

[`ClipExtractor`](../../src/business-logic/clip-extractor.ts) validates exact-only requests before crossing [`IClipExtractionService`](../../src/business-logic/clip-extraction-service.ts). [`ClipExtractionWorkflow`](../../src/app/clip-extraction-workflow.ts) owns single/batch progress, cancellation, per-range outcomes, and publication retry without re-encoding; [`ExtractionPublisher`](../../src/app/extraction-publisher.ts) owns lazy reuse/creation of the movie-stem collection and emits a collection-published event only after durable membership persistence. For a collection destination it reads only its target collection, with `CollectionDescriptionValidator` (the same rules as opening a folder): an empty file is an empty collection, and a file with duplicate entries refuses the extraction before anything is encoded rather than being rewritten. A folder destination writes no collection and reads none. `Collection.withExtractionOutput` decides where a new output goes. [`OpenFolderRefresher`](../../src/app/open-folder-refresher.ts) owns the response policy: it re-enumerates a matching, already-open clean folder immediately, or defers one refresh until the active Collection is successfully saved. [`FolderSelectionWorkflow`](../../src/app/folder-selection-workflow.ts) owns active-folder reload, including preservation of the selected collection. The renderer sends only opaque source/destination handles and validated names. [`ClipExtractionRuntime`](../../electron/clip-extraction-runtime.cjs) resolves the original prepared-review source and selected stream in the main process. For an unchanged original source, [`FrameReviewHost`](../../src/frame-review/host/frame-review-host.ts) reads a bounded ordered frame-timestamp window from the already open BestSource index; the runtime seeks near that window, selects by indexed integer PTS, verifies every selected source timestamp and final frame count, and muxes nearby audio. Integer PTS selection avoids floating time-boundary rounding; missing or ambiguous index timing, normalization, or failed verification still uses the original exact full-decode route. The runtime publishes `<collection-name>-NNN.mp4` exclusively without overwrite. Main-process progress crosses IPC with an operation ID; the adapter discards stale events. The shared Clips panel and Refine Gif show current clip, stage, encoded frames when available, and Cancel. Cancel aborts active media work and stops later ranges; a clip already created is published or left in recoverable publication-failed state. Collection persistence is atomic, output allocation is serialized per destination collection, and a membership-save failure can be retried without launching FFmpeg again.

For new MP4 output, the extraction runtime gets trusted endpoint hashes from the prepared BestSource index and asks [`Mp4Provenance`](../../electron/clip-provenance/mp4-provenance.cjs) to write and read back the bounded `clip-sandbox.prov.v1` movie tag. It records the sampled source fingerprint and inclusive canonical original-source ordinals, never the private path. A metadata-specific mux failure retries with the encoded video and no tag; a readback failure reports a warning after successful media and Collection publication. Existing clips and clips without valid provenance remain loadable.

Clips with valid provenance expose Refine in the right-click menu from both the folder's full clip list and a saved collection; otherwise `GridContextMenuWorkflow` passes a `ClipRefineAvailability` and the disabled item shows the reason (no source movie info, or the info could not be read) as a visible second line. [`CollectionClipRefinement`](../../electron/collection-clip-refinement.cjs) reads the MP4 tag in the trusted process, checks the remembered capture-store path first, searches granted and catalogued pipeline folders second, and asks the user for a source movie if neither matches the fingerprint. The contextual Refine screen opens before source resolution and displays lookup/preparation progress there. [`CollectionClipRefinementSession`](../../src/app/collection-clip-refinement-session.ts) opens that source and imports the tagged exact range only in memory (`RangeCaptureModel.withExactRange`, with unsaved capture storage); it never attaches the range to the movie's saved capture queue. The existing Refine screen and shared player handle frame adjustment. Locked ranges remain available for exact A/S jumps and loop preview, and the Clips panel's Refine action starts a new editing session for that range. [`ExtractionPublisher`](../../src/app/extraction-publisher.ts) targets the selected collection and persists membership when Refine began there; from the folder's full clip list it publishes the new media to that folder without writing a collection file. Ordinary GIF extraction still publishes to `extraction-tmp`. Unsaved changes in the current clip sequence must be resolved before opening a clip for refinement, and the contextual screen remains active during extraction, so later saves cannot overwrite new membership.

Start thumbnails are ephemeral renderer-generated PNGs. [`ElectronThumbnailCacheService`](../../src/adapters/electron/electron-thumbnail-cache-service.ts) bounds and validates PNG payloads, exposes only Blob URLs plus opaque ids, and revokes URLs it owns. [`ThumbnailCacheRuntime`](../../electron/thumbnail-cache-runtime.cjs) owns `userData/cache/thumbnails`, validates ids and payloads again, and never returns a path. Electron clears that directory at startup and on normal shutdown after native review hosts close; persistent `frame-index-cache`, `playback-proxy-cache`, and `exact-review-proxy-cache` entries are unaffected. `GifRangesPanelControl` renders the complete shared queue with start pictures, exact/inexact labels, accessible Refine entry points, and the selected range highlighted; it does not own the queue. Tests: range/refinement/session/cache unit tests and panel/screen integration tests. The remaining native GIF output checks are in [`gif-extraction-output.spec.ts`](../../tests/e2e/gif-extraction-output.spec.ts).

Renderer shutdown is ordered but remains best-effort because a browser page cannot hold Electron quit open. [`ApplicationShutdownCoordinator`](../../src/app/application-shutdown-coordinator.ts) first deactivates the shell and releases global input/resize sources, then awaits both GIF sessions' `dispose()` so extraction cancellation, movie review disposal, subscription detachment, and thumbnail cleanup precede destruction of the shared player and global controls. The trusted process is the authoritative close barrier: [`electron/main.cjs`](../../electron/main.cjs) prevents final quit until frame-review hosts and the clip-extraction runtime have disposed, then removes ephemeral thumbnails. Active FFmpeg/native work receives abort, operation-owned temporary directories are removed, and validated prepared-review caches deliberately survive shutdown.

The main-process quit barrier also awaits pending capture-store writes before closing; per-movie `clip-captures` records survive app restarts.

### Activity and Errors

[`ActivityLogger`](../../src/app/activity-logger.ts) is the session-history owner. Activity producers receive its instance, an adapter to its typed `log` contract, or an [`ActivityReporter`](../../src/app/activity-reporter.ts) (success/progress/failure over the logger) from `AppController`; they do not call the panel. Reporting follows the layer: app-layer components (workflows, sessions, policies) receive the reporter injected, while UI controls never report themselves; they emit failure events, and [`ControlFailureReporting`](../../src/app/control-failure-reporting.ts) decides whether each goes to Activity or only to the diagnostics log. There is no global reporter. [`ActivityPanelAutoOpenPolicy`](../../src/ui/activity-panel-auto-open-policy.ts) answers whether an error may open the panel. Entries have a message, optional extra text, and ordered named fields for variable detail. Errors also carry affected-operation/recovery text, optional technical details, and an optional retry capability supplied by the caller. Stable error ids support explicit resolution. Retention keeps the newest 50 non-error/resolved entries plus every unresolved error; bulk clear preserves unresolved errors, while each error offers explicit dismissal. No notification database or global singleton is added.

The control listens to logger changes and owns history keyboard navigation, native wheel scrolling without scrollbar chrome, detail expansion and local copy/retry interaction. The application injects clipboard writing directly; failures stay inside the entry. Settings supplies a retry that reapplies only the failed preference against the current committed settings, returning a typed failure to the existing entry. Folder/collection/video-edit errors provide available context without automatically replaying destructive operations. Tests: `activity-logger.spec.ts`, `activity-indicator-control.spec.ts`, `settings-screen.spec.ts`, app-controller integration protection checks and [`activity.spec.ts`](../../tests/e2e/activity.spec.ts).

### Folder Load

Read these first:

1. [`electron/preload.cjs`](../../electron/preload.cjs)
2. [`src/adapters/electron/electron-folder-service.ts`](../../src/adapters/electron/electron-folder-service.ts) and, for Pipelines, [`electron-pipeline-catalog-service.ts`](../../src/adapters/electron/electron-pipeline-catalog-service.ts)

4. [`src/business-logic/PipelineFactory.ts`](../../src/business-logic/PipelineFactory.ts)
5. [`src/domain/pipeline.ts`](../../src/domain/pipeline.ts)

Flow:

1. `FolderSelectionWorkflow` handles the toolbar's browse request or a Pipelines catalog load (behind the unsaved-changes prompt), and the renderer asks the preload bridge to pick a folder,
2. Electron main enumerates top-level files from the chosen folder and returns lightweight metadata plus collection-file text and video media URLs; absolute paths remain an existing filesystem/edit compatibility field but do not enter the renderer frame-review service contract,
3. `ElectronFolderService` converts those records into plain [`FolderEntry`](../../src/business-logic/folder-entry.ts) values (name, type, media address, desktop path, and text for `.txt` files),
4. `PipelineFactory.buildPipeline(...)` classifies videos and `.txt` collection files, reads each collection from its entry's text through `CollectionTextFormat`, turns videos into `ClipSource` values, then builds the durable `Pipeline`,
5. the initial active selection is pipeline mode, and `PipelineWorkingCopy.loadPipeline(...)` materializes a runtime `ClipSequence` over canonical clips, creating generated ids only for video files not yet represented by a runtime `Clip`,
6. collection selection uses `Pipeline.getCollectionByFilename(...)` plus `PipelineWorkingCopy.materializeSelection(...)` / `activateSelection(...)` to re-materialize a runtime `ClipSequence` from the chosen `Collection` against the current pipeline's canonical clips,
7. the grid controller renders that runtime sequence and owns card DOM, selection UI, drag/drop, media-element lifecycle, and card-video metadata capture.
8. flows that durably add files, such as exact extraction, publish an explicit completion event rather than watching the filesystem; `OpenFolderRefresher` re-enumerates an already-open matching clean folder, or defers the refresh until its active Collection save succeeds.

### Selection Switching and Persistence

Read these first:

1. [`src/domain/pipeline.ts`](../../src/domain/pipeline.ts)
2. [`src/domain/collection.ts`](../../src/domain/collection.ts)
3. [`src/adapters/electron/electron-folder-file-service.ts`](../../src/adapters/electron/electron-folder-file-service.ts)
4. [`src/app/collection-view-workflow.ts`](../../src/app/collection-view-workflow.ts), [`src/app/collection-save-workflow.ts`](../../src/app/collection-save-workflow.ts), [`src/app/add-to-collection-workflow.ts`](../../src/app/add-to-collection-workflow.ts), [`src/app/trash-clips-workflow.ts`](../../src/app/trash-clips-workflow.ts) and [`src/app/collection-file-writer.ts`](../../src/app/collection-file-writer.ts)

Flow:

1. `Pipeline` owns the current folder's available video files, canonical runtime clips, and saved collections,
2. `PipelineWorkingCopy` owns the active selection; `activeCollection === null` means pipeline mode,
3. switching selections re-materializes a runtime `ClipSequence` through `PipelineWorkingCopy`, which delegates to `Pipeline.materializePipeline(...)` or `Pipeline.materializeCollection(...)` and reuses canonical `Clip` objects so loaded metadata survives view switches,
4. saving an existing collection writes the active `ClipSequence` back to that collection's backing file,
5. saving from pipeline view creates a new `Collection`; the pipeline view itself is never persisted,
6. add-to-collection, save, and Recycle Bin flows are orchestrated by `AddToCollectionWorkflow`, `CollectionSaveWorkflow` and `TrashClipsWorkflow` (files go to the operating system trash through `shell.trashItem` in the `clip-sandbox:trash-files` IPC handler, never `unlink`): `Pipeline` owns the durable in-memory mutation rules, `PipelineWorkingCopy` owns active-sequence state and dirty tracking, and `CollectionFileWriter` performs the raw collection-file writes through [`ElectronFolderFileService`](../../src/adapters/electron/electron-folder-file-service.ts). A new collection name gets two separate checks: `CollectionNameValidator` decides whether the name is valid, and `Pipeline.hasCollectionWithFilename` (through `NewCollectionNameCheck`) decides whether it already exists. Save as Collection is awaitable and settles as `saved`, `cancelled` or `failed`, which the unsaved-changes prompt and the Recycle Bin preflight use before continuing; its panel is not modal, so a request made while it is open takes it over and the earlier caller's wait settles as `cancelled`, leaving only the latest flow to resume. A Recycle Bin request keeps the folder it was built for and moves nothing if another folder is open when it is confirmed,
7. remove-from-view is only a collection-view behavior; in pipeline view, the Delete key routes to the move-to-Recycle-Bin flow.

3. rendered card videos populate `Clip` duration and intrinsic dimensions through `loadedmetadata`; `GridVideoMetadataTracker` tracks active-sequence metadata completion/failure so the normal grid can perform at most one metadata-based correction relayout,
4. `ClipCollectionGridControl` owns a per-loaded-pipeline grid-view cache keyed by pipeline view or collection filename; switching views reuses cached, still-mounted grid/card/video DOM when the ordered clip ids still match, with inactive grids kept invisible and out of flow, while `CollectionViewWorkflow` and the mutating workflows only supply view keys and invalidate views after sequence membership/order changes,
5. `DisplayLayoutRules` owns normal and fullscreen grid calculations; normal scoring maximizes expected contained video area using known clip dimensions with a deterministic fallback aspect ratio,
6. reorder emits ordered clip ids as a grid event to `CollectionViewWorkflow`, which delegates active `ClipSequence` mutation and dirty-state tracking to `PipelineWorkingCopy`; drag-and-drop and Alt+Arrow share one move path in the grid. The selector's Unsaved marker and the toolbar's Save button follow `hasDirtyClipSequenceChanges` through `CollectionViewWorkflow.refreshSelector`/`refreshToolbar`, and Save emits the same `saveRequested` as Actions → Save,
7. keyboard: the grid keeps one card as the Tab stop (the last focused, else the first selected, else the first card); [`GridNavigationRules`](../../src/ui/grid-navigation-rules.ts) maps arrow keys to card indexes using the applied column count. Shift+F10/Menu emit `contextMenuRequested` with `fromKeyboard`, positioned at the card, and the menu then focuses its first item; the contextmenu event Chromium sends after the Menu key (`button === -1`) is ignored. Closing Zoom returns focus to the clip it showed,
8. zoom is clip-centric at the app level but the overlay stays media-source-oriented and now exposes a right-click seam for zoom-only edit actions,
9. the toolbar activity indicator replaces the old footer toast and is now the shared surface for load/save/delete/edit messages,
10. fullscreen is coordinated by `CollectionFullScreenWorkflow`, using grid layout rules plus fullscreen adapters.

Flow:

1. zoom mode opens a context menu via [`src/ui/zoom-edit-menu-control.ts`](../../src/ui/zoom-edit-menu-control.ts),
2. `ZoomWorkflow` resolves the current zoomed `Clip` and passes `{ edit, sourceClip, folderAccess }` to `ZoomVideoEditWorkflow`,
3. `ZoomVideoEditWorkflow` guards concurrent edits, delegates execution to `ClipEditor`, and emits started/created/failed/finished callbacks,
4. `ClipEditor` derives the preferred `[base]-looped.mp4` filename and hands the request to the Electron-backed video-edit service,
5. the trusted runtime resolves `ffmpeg` through [`NativeProductLocator`](../../electron/native-product-locator.cjs), chooses a collision-free destination, runs the loopify command, and returns folder-entry metadata,
6. `ZoomWorkflow` callbacks convert that metadata back into a renderer file, ask `PipelineWorkingCopy` to insert the created clip into pipeline or collection mode, reselect the new clip, update status/toolbar, and reopen zoom.

## Risky Seams

1. [`src/app/app-controller.ts`](../../src/app/app-controller.ts) is the single place that knows both controls and workflows. Construction order matters: workflows must subscribe before `ApplicationShellControl.start()` emits the first `screenChanged`. Workflows that call each other (for example the folder reload used by refresh) are connected here, and keeping that set small keeps the flows independently testable.
2. [`src/ui/clip-collection-grid-control.ts`](../../src/ui/clip-collection-grid-control.ts) owns DOM rendering, selection, drag/drop, and media-element sources. Changes can affect both UI behavior and lifecycle cleanup.
3. [`electron/preload.cjs`](../../electron/preload.cjs) and [`electron/main.cjs`](../../electron/main.cjs) define the desktop trust boundary. Over-broad IPC or preload exposure is the main architecture risk in this runtime.
4. [`src/app/collection-full-screen-workflow.ts`](../../src/app/collection-full-screen-workflow.ts) owns fullscreen timers and input while the grid owns cancelable media rotation. Exit, view replacement and disposal must cancel pending ended listeners.
5. The current view contract is intentionally split: `Pipeline` and `Collection` are durable models, while `PipelineWorkingCopy` owns the active mutable `ClipSequence` working copy. Changes here can silently break dirty-state tracking, save enablement, and delete semantics.
6. The TypeScript migration now has strict authored-source coverage enforced by `npm run typecheck` through [`tsconfig.strict-src.json`](../../tsconfig.strict-src.json). Authored TypeScript under `src/` should not use `// @ts-nocheck`; the remaining unchecked runtime bridge is the CommonJS Electron shell under [`electron/`](../../electron/), which is intentionally outside this strict source config for now.

### Shell remediation verification (2026-09-09)

[`IShortcutDescriptor`](../../src/ui/app-screen.ts) represents optional explicit groups and alternative complete key sequences; each sequence is a chord. [`KeyboardMapControl`](../../src/ui/keyboard-map-control.ts) renders these as static keycaps, while KeyboardMapControl owns its Close button and requests dismissal through [`GlobalUtilityCoordinator`](../../src/ui/global-utility-coordinator.ts). ### Shell component boundaries (ownership correction)

`CollectionScreen` coordinates initial focus through `focusSelectedClip()` on the grid and `focusBrowse()` on the toolbar. It does not query child markup or calculate grid padding. `ClipCollectionGridControl` owns selected-card focus and reads its allocated container height minus current vertical padding. Its existing optional height provider remains available to standalone callers.

`FoldablePanelControl.targetWidth` owns the interpretation of panel state and sizing CSS; the shell sums those public measurements. Screen roots, command surfaces, utility panels and triggers are explicit mounting/visibility contracts, not permission to inspect descendants. Keyboard and Activity controls handle their own Close buttons and call injected close requests. The coordinator handles exclusivity, outer-surface visibility, placement and focus return. Fullscreen button rendering belongs to `MainToolbarControl`; the fullscreen session reports state through an injected callback. Activity auto-open asks Zoom, Save and Conflict controllers about their state; the remaining generic open-dialog query detects the browser dialog surface rather than a component's private selectors.


### Encapsulation corrections (2026-09-10)

Grid ownership includes normal/fullscreen DOM layout, visibility buffers and rotation completion. `rotateVisibleClip()` switches intact cards using visibility and CSS order; sources, metadata callbacks and canonical IDs stay together, and the outgoing visual slot is retained. `cancelRotation()` removes the pending listener and restores looping; restore/render/invalidation/disposal invoke it. `fsApplySlots(slots)` receives a value instead of a shared state bag. The composition root no longer obtains grid descendants for layout; `DomRendererAdapter` and the raw grid getter were removed. Pure grid calculations remain injectable, as does standalone height allocation.

The grid's implementation fields/helpers, dialog/menu fields, metadata tracker state, Zoom DOM and adapter dependencies are private. Public callbacks carry semantic selection/point data, not cards. Explicit outer mounting/visibility surfaces remain legitimate contracts. These are TypeScript encapsulation boundaries, not a security sandbox against arbitrary JavaScript reflection.

`PipelineWorkingCopy.hasDirtyClipSequenceChanges` compares the current sequence to the saved collection or pipeline every read; mutation through a shared sequence cannot leave a stale flag. Canonical mutable Clip identities remain shared deliberately. `Clip` and `Pipeline` hold frozen `ClipSource` values and reject anything else at run time, so outside code cannot change or split a clip's source. A created edit output becomes a `ClipSource` through `ElectronFolderService.clipSourceOf` before Zoom inserts it. Desktop-path edit contracts remain an explicit Windows-first tradeoff, rather than an implicit private-state dependency.

Acceptance and remaining scope: [encapsulation correction verification](../research/encapsulation-fixes-verification.md). The historical review is a before-state inventory, not a current list of open defects.


### Edit callback recovery (2026-09-10)

`ZoomVideoEditWorkflow` guarantees running-state reset and a finishing notification even when lifecycle callbacks throw. Callback failures propagate as `VideoEditNotificationError`, retaining the actual edit result (null if editing never began) and all notification errors. The app reports created output separately from edit failure and preserves technical details; it does not automatically repeat disk operations. See [verification and playback assessment](../research/editing-recovery-and-playback-assessment.md). Zoom now reports active-video playback failures through `onPlaybackFailure({ clipId, name, error })`. Zoom owns attempt generations and deduplication; closed/replaced/superseded attempts and rejections after a playing event are ignored. The app presents Activity recovery guidance and records native error details. Background grid diagnostics retain their existing behavior.
