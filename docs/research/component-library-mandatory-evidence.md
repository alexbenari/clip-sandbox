# Mandatory component-library candidate evidence

Research captured 2026-09-06 for Milestone 1 of `application-shell-and-global-surfaces-exec-plan.md`. This fragment covers only the three user-nominated candidates. It records evidence and bounded inferences; it makes no adoption or shortlist decision.

## Method and comparison boundary

Sources were restricted to official project sites, official GitHub repositories/API pages, and npm registry metadata. GitHub stars/forks and repository state are point-in-time signals, not quality measures. Issue/PR observations are named samples, not aggregate responsiveness claims. “No policy located” means GitHub's community profile and the expected root `SECURITY.md` path exposed none; it does not prove no private reporting route exists. Offline plausibility assumes dependencies/assets are installed or copied before packaging and that the Electron renderer makes no network request at run time.

Clip Sandbox is currently a framework-free Electron renderer with local CSS/TypeScript controllers and a compact dark system defined by `DESIGN.md`. Relevant needs include trees, foldable/split panels, drag targets, buttons, selectors/comboboxes, switches, fields, dialogs, menus/popovers/tooltips, progress/status, tabs, virtualized data surfaces, keyboard-command surfaces, and future media-editor primitives.

## Astryx (`facebook/astryx`)

**Category, runtime, ownership.** Astryx is a cohesive, source-ejectable design system in public beta. Its official README requires React 19+, React DOM 19+, and StyleX; npm lists those three as peers, plus `intl-messageformat`. Consumers import compiled CSS and typed React components, can override classes/CSS custom properties, or use `astryx swizzle` to eject source into the application. This is materially different from Clip Sandbox's present DOM/controller architecture: runtime use entails adopting React for the relevant renderer surface; ejection entails owning the copied React component and its future fixes. Sources: [README](https://github.com/facebook/astryx#readme), [core quick start](https://github.com/facebook/astryx/blob/main/packages/core/README.md#quick-start), [npm package](https://www.npmjs.com/package/@astryxdesign/core).

**Control breadth.** The repository claims 150+ components. Directly listed core modules cover the immediate inventory well: `TreeList`, `Resizable`, `Collapsible`, `AppShell`, `SideNav`, `Button`/`IconButton`, `Selector`/`ComplexSelector`/`Typeahead`, `Switch`, field/input families, `Dialog`/`AlertDialog`, menus, `Popover`, `Tooltip`, `ProgressBar`/`Spinner`/`StatusDot`, `TabList`, `CommandPalette`, `Table`, `Grid`, `Slider`, `Toolbar`, and overlay/lightbox/navigation primitives. The evidence establishes breadth, not that every control meets Clip Sandbox interaction requirements or that `Table`/`Grid` virtualizes. Sources: [core source index](https://github.com/facebook/astryx/tree/main/packages/core/src), [architecture overview](https://github.com/facebook/astryx#architecture). Confidence: high for catalog presence; medium for fitness until component spikes.

**Theming and visual fit.** Astryx exposes CSS custom-property themes, seven first-party themes, CSS-layer imports, class overrides, theme targets, dark mode, and source ejection. These are credible normalization hooks for Clip Sandbox's color/radius/density vocabulary. The cost is adapting a broad system whose defaults and theme API are still moving during beta. Sources: [README customization description](https://github.com/facebook/astryx#overview), [core theming/setup](https://github.com/facebook/astryx/blob/main/packages/core/README.md#quick-start), [v0.5.2 release](https://github.com/facebook/astryx/releases/tag/v0.5.2).

**Accessibility: claim versus proof.** The README calls the components accessible. Public process evidence is stronger than the claim alone: the repo exposes an [accessibility checklist](https://github.com/facebook/astryx/wiki/Accessibility-Checklist); package scripts include an axe/Playwright audit that fails on new violations; and recent release notes discuss screen-reader announcements and focus order. This proves an active accessibility engineering process, not WCAG conformance of every component or correct behavior in Clip Sandbox. Source: [repository package scripts](https://github.com/facebook/astryx/blob/main/package.json). Confidence: high for the process, medium for product-level accessibility pending manual AT/keyboard testing.

**License and assets.** Root code is MIT, copyright Meta Platforms, Inc. The neutral theme identifies Lucide icons, also an MIT-licensed project, but this review did not trace every demo image, banner, font, or sample-media asset. Do not infer that all repository presentation assets are cleared for redistribution merely from the code license. Sources: [Astryx LICENSE](https://github.com/facebook/astryx/blob/main/LICENSE), [neutral theme reference](https://github.com/facebook/astryx/tree/main/packages/themes/neutral), [Lucide license](https://github.com/lucide-icons/lucide/blob/main/LICENSE). Confidence: high for package code; low-to-medium for unenumerated demo assets.

**Governance, lifecycle, documentation, community.** Meta owns the repository; it provides contribution guidance, a code of conduct, API/design/component-lifecycle rubrics, hosted docs, Storybook, sandbox, Discord, and a CLI whose commands expose component docs, templates, token/theme docs, source ejection, upgrade codemods, discovery, and gap reporting. GitHub showed 12,806 stars and 1,114 forks. These are strong visibility/documentation signals, while the January 2026 repository creation date and beta/0.x status leave limited public upgrade history. Sources: [repository](https://github.com/facebook/astryx), [contributing](https://github.com/facebook/astryx/blob/main/CONTRIBUTING.md), [docs](https://astryx.atmeta.com), [Storybook](https://facebook.github.io/astryx/storybook/), [CLI README](https://github.com/facebook/astryx/blob/main/packages/cli/README.md).

**Release, activity, sampled response.** Latest stable GitHub/npm release was `0.5.2`, published 2026-08-30; npm had continued `0.5.2-canary.*` publication through 2026-09-06. The sampled latest commit was [`b2e6a1d`](https://github.com/facebook/astryx/commit/b2e6a1d6b0fb9e5ca976b4d53f29f1b476ec3f61), 2026-09-06. Three sampled recent merged PRs took about 3.4 days ([#5932](https://github.com/facebook/astryx/pull/5932)), 1.4 days ([#6049](https://github.com/facebook/astryx/pull/6049)), and 26 minutes ([#6075](https://github.com/facebook/astryx/pull/6075)) from creation to merge. Sample issue [#5900](https://github.com/facebook/astryx/issues/5900) was closed after about 4.3 days with a maintainer comment linking and verifying the fix. This sample supports current activity, not a general response-time guarantee.

**Security, migration, offline Electron.** Astryx publishes a [security policy](https://github.com/facebook/astryx/blob/main/SECURITY.md) directing private reports to Meta Bug Bounty and supporting only the latest released package version. Migration help is explicit through `astryx upgrade --apply` codemods and per-release changelogs, though its short 0.x history means stability is not yet demonstrated across major versions. npm reports `@astryxdesign/core@0.5.2` at about 18.5 MB unpacked/2,893 files before React, React DOM, StyleX, and a theme. Compiled local JS/CSS makes offline Electron plausible after packaging, but React 19 adoption, bundle impact, CSP behavior, and any component that fetches external assets require a spike. Confidence: high for technical plausibility; low for migration cost into the existing renderer.

## Semantic UI (`Semantic-Org/Semantic-UI`)

**Category, runtime, ownership.** Semantic UI is a cohesive HTML/CSS/JavaScript framework built with Less/Gulp. Its packaged JavaScript depends on jQuery; the main `semantic-ui` npm package also brings a large build/install dependency set. A CSS-only distribution exists. It can decorate ordinary HTML without converting the renderer to React, but interactive modules use Semantic's jQuery plugin runtime. Sources: [README](https://github.com/Semantic-Org/Semantic-UI#readme), [package manifest](https://github.com/Semantic-Org/Semantic-UI/blob/master/package.json), [CSS distribution](https://github.com/Semantic-Org/Semantic-UI-CSS).

**Control breadth.** The source has six groups: globals, elements, collections, views, modules, and behaviors. It covers buttons, inputs, lists, loaders, labels, menus, forms, tables, cards/items, accordion, checkbox, dropdown/search, modal/dimmer, popup/tooltip use, progress, rating, sidebar, tabs, sticky, transitions, and visibility/form validation. It does not expose a first-party hierarchical tree, virtualized list/grid, command palette, or dedicated resizable split-panel component in the inspected catalog; those would remain local or secondary-library responsibilities. Sources: [definitions tree](https://github.com/Semantic-Org/Semantic-UI/tree/master/src/definitions), [component site](https://semantic-ui.com/introduction/getting-started.html). Confidence: high for catalog presence/absence at the named source path.

**Theming and visual fit.** The framework was explicitly designed for theming and claims 3,000+ variables with three levels of inheritance. Its Less theme/config workflow can replace site variables and element overrides, and its broad component CSS can be built selectively. This gives substantial styling control, but integrating a legacy global class/CSS framework with Clip Sandbox's current selectors and compact token system raises collision and normalization risk. Sources: [theming guide](https://semantic-ui.com/usage/theming.html), [README key features](https://github.com/Semantic-Org/Semantic-UI#readme).

**Accessibility: claim versus proof.** No broad accessibility commitment, conformance statement, security-style accessibility policy, or automated axe equivalent was located in the inspected official README, package scripts, and source-level test/build metadata. Individual controls expose some ARIA-related options/markup, but that is not system-level proof. Historic official issue [#6641](https://github.com/Semantic-Org/Semantic-UI/issues/6641) explicitly tracks accessibility gaps. Treat accessibility as unproven and require component-by-component keyboard/AT testing. Confidence: medium; absence findings are limited to the inspected public surfaces.

**License and assets.** Source is MIT. The distribution includes theme assets such as icon fonts and images; this pass did not locate an official asset-by-asset license inventory in the core repository. The MIT root license is clear for Semantic UI's software, but third-party font/image provenance should be verified before redistribution. Sources: [LICENSE](https://github.com/Semantic-Org/Semantic-UI/blob/master/LICENSE.md), [default theme assets](https://github.com/Semantic-Org/Semantic-UI/tree/master/src/themes/default/assets). Confidence: high for framework code; low-to-medium for every bundled asset.

**Governance, lifecycle, documentation, community.** The repository belongs to `Semantic-Org`; `package.json` identifies Jack Lukic as author, and the README directs support to Stack Overflow/Gitter and contributions to the `next` branch. It has contribution and issue/PR templates, but no code of conduct or security policy was exposed by GitHub's community profile. The component/theming documentation is extensive and example-rich, yet visibly dated: its browser-support matrix still names IE11, Android 4.4, Edge 12, and the site's “New” page is “New in 2.4.” GitHub showed 51,017 stars and 4,851 forks, strong historical adoption signals that do not establish current maintenance. Sources: [repository](https://github.com/Semantic-Org/Semantic-UI), [contributing guide](https://github.com/Semantic-Org/Semantic-UI/blob/master/CONTRIBUTING.md), [New in 2.4](https://semantic-ui.com/introduction/new.html).

**Release, activity, sampled response.** Latest GitHub/npm release is `2.5.0`, published 2022-10-06. The sampled latest commit was [`597843a`](https://github.com/Semantic-Org/Semantic-UI/commit/597843ab84d565cccfd8fd7719416350ae73e734), 2024-11-27. Recent closed-PR samples were old submissions closed without merge after years: [#6683](https://github.com/Semantic-Org/Semantic-UI/pull/6683), [#5915](https://github.com/Semantic-Org/Semantic-UI/pull/5915), and [#6664](https://github.com/Semantic-Org/Semantic-UI/pull/6664). Sample issue [#7156](https://github.com/Semantic-Org/Semantic-UI/issues/7156) was closed in about 55 minutes with no comment; [#7159](https://github.com/Semantic-Org/Semantic-UI/issues/7159) remained open with only a non-maintainer comment at retrieval. These samples show triage/closure activity but no recent merged development response.

**Security, migration, offline Electron.** No repository security policy was located. The visible migration history is release notes and the old `next`-branch process; no maintained major-version migration tooling was found. npm reports `semantic-ui@2.5.0` at about 13.2 MB unpacked/701 files, with jQuery plus numerous Gulp-era install dependencies; the CSS-only package avoids runtime plugins but also their behavior. Local CSS/JS can run offline in Electron, but build reproducibility on the current Node toolchain, global CSS impact, jQuery ownership overlap, and unresolved accessibility behavior need a clean-install/spike check. Confidence: high for offline possibility; medium-to-low for maintainable integration.

## UIverse / Galaxy (`uiverse-io/galaxy`)

**Category, runtime, ownership.** UIverse is a community gallery and Galaxy is its generated archive, not a governed runtime component library. The site offers copyable HTML/CSS, Tailwind, React, and Figma variants; Galaxy contains standalone HTML files and no package manifest. The README says submissions are reviewed on UIverse, automatically uploaded, and direct repository PRs are ignored. Each copied element becomes application-owned source. Sources: [UIverse](https://uiverse.io/), [Galaxy README](https://github.com/uiverse-io/galaxy#readme), [Galaxy repository](https://github.com/uiverse-io/galaxy).

**Control breadth.** Galaxy claims over 3,000 elements. Its repository categories are Buttons, Cards, Checkboxes, Forms, Inputs, Notifications, Patterns, Radio buttons, Toggle switches, Tooltips, and loaders; the site highlights loading UI, button effects, cards, forms/inputs, tooltips, and decorative patterns. It does not present a coherent tree, virtualized grid, split panel, command surface, dialog/menu/popover system, or shared behavioral API. Breadth is strongest in visual leaf controls and micro-interactions, weak for the structural/accessibility-heavy controls in the Milestone 1 inventory. Sources: [Galaxy root](https://github.com/uiverse-io/galaxy), [UIverse collections](https://uiverse.io/). Confidence: high for repository categories; medium for site-wide absence because the gallery changes independently of the stale archive.

**Theming and visual fit.** There is no shared theme API or token contract. Copy ownership makes any snippet restylable, including conversion to `DESIGN.md` tokens, but consistency, focus states, reduced motion, and future maintenance become Clip Sandbox's responsibility per snippet. The gallery's strong decorative/animated emphasis may require substantial normalization for the restrained screening-room visual language. Source: [UIverse home/gallery](https://uiverse.io/). Confidence: high.

**Accessibility: claim versus proof.** No gallery-wide accessibility guarantee, conformance report, automated accessibility suite, or component contract was found in the official site/repository surfaces inspected. Because submissions come from many creators as raw markup/CSS, semantic elements, keyboard behavior, focus styling, contrast, motion reduction, and accessible names must be audited per copied element. Visual approval by the platform is not accessibility proof. Confidence: medium-to-high for the repository; the private website pipeline may have checks not publicly documented.

**License and assets.** Galaxy's README and root license put all archived UI elements under MIT and request optional attribution to the original creator and UIverse. That is clear for checked-in element source. Individual snippets may reference remote fonts, images, icons, or creator-supplied content whose separate rights and offline availability are not itemized by the root license; audit and localize every chosen asset. Sources: [licensing statement](https://github.com/uiverse-io/galaxy#licensing-and-attribution), [LICENSE](https://github.com/uiverse-io/galaxy/blob/main/LICENSE). Confidence: high for archived source, low-to-medium for external assets.

**Governance, lifecycle, documentation, community.** `uiverse-io` owns the repository; curation happens on the website and Galaxy is automatically fed. The repo has no contributing guide, code of conduct, issue template, package/release process, or API documentation; its README explicitly rejects direct PRs. The site offers visual browsing, search/tags, code retrieval, profiles, and Figma copy, which is useful discovery documentation but not a stable component API. GitHub showed 12,475 stars and 878 forks. These indicate reach, while the website-controlled pipeline limits transparent repository governance. Sources: [organization](https://github.com/uiverse-io), [Galaxy README](https://github.com/uiverse-io/galaxy#readme), [UIverse](https://uiverse.io/).

**Release, activity, sampled response.** Galaxy has no GitHub releases or tags. The sampled latest commit was [`adbd2ad`](https://github.com/uiverse-io/galaxy/commit/adbd2adde0a299a3956ea288fb444ec01891ca41), 2024-09-02, despite the live site continuing to change. Issue [#18](https://github.com/uiverse-io/galaxy/issues/18), a concrete UIverse website bug filed 2025-09-15, remained open with zero comments at retrieval. Issue [#8](https://github.com/uiverse-io/galaxy/issues/8) closed after roughly 20 months with three comments. The only two sampled closed PRs, [#16](https://github.com/uiverse-io/galaxy/pull/16) and [#4](https://github.com/uiverse-io/galaxy/pull/4), were closed unmerged, consistent with the README's “PRs ignored” policy. This repository is therefore poor evidence for current website cadence or conventional maintainer responsiveness.

**Security, migration, offline Electron.** No repository security policy was located. There is no versioned package or migration mechanism; copying freezes a local snapshot, so upstream changes are manual discovery/review work. Plain copied HTML/CSS is highly plausible offline and has no mandatory runtime dependency, provided remote fonts/images/icons are removed or packaged. React/Tailwind variants add their own dependencies, and arbitrary community CSS/markup must be treated as untrusted source and reviewed before inclusion. Confidence: high for simple snippets; low for any uninspected element.

## Cross-candidate uncertainties for Milestone 2

- Astryx's catalog and governance evidence are current, but beta API churn, React migration scope, true bundled cost, virtualized-data behavior, and Electron CSP/offline behavior remain unproven.
- Semantic UI's component and theming breadth are documented, but current security ownership, modern accessibility quality, Node/build compatibility, and a sustainable upgrade path remain unclear.
- UIverse's site is more current than Galaxy, so repository dates cannot date the live gallery. Every proposed snippet needs its own provenance, dependency, accessibility, responsive, motion, and external-asset audit.
- None of the three has been run in Clip Sandbox in this research-only milestone; all visual-normalization and interaction-fit statements are bounded inferences from official artifacts.
