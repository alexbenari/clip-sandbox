# Feature Spec: Persistent GIF Captures and Extraction Provenance

Status: Signed off by user (2026-09-27). Execution plan and formats approved (2026-09-28). Draft persistence added by user request (2026-09-28).

## 1. Goal

GIF captures, including the active unfinished draft and locked ranges not yet fully published, survive screen changes, movie changes, and app restarts. They remain associated with the movie from which they were captured. Each newly extracted MP4 attempts to carry its source movie and inclusive original start/end frames without relying on the app's capture store. That record can support a future feature that reopens the verified source and extends an extracted clip beyond its current boundaries. Missing clip provenance does not make a clip unusable.

The existing GIF Extraction and Refine screens remain the places where captures are shown and acted on. A separate handoff covers screen-declared initial side-panel fold preferences; that work is outside this spec.

## 2. Movie identity and reopening

- A saved movie queue is keyed by a versioned **source fingerprint** based on the source-content fields currently used to build the prepared-review cache identity: sampled packet digest and its profile version, source size and duration, selected video stream, and stream-metadata digest. The full prepared-review cache key is not a movie ID because it also includes native/tool and preparation versions. A sampled fingerprint is not a full-file cryptographic proof. On reopen, the trusted process recomputes and compares that fingerprint before attaching the queue. For an exact range, immediately before Refine or Extract uses it, the trusted frame index retrieves the saved start/end canonical ordinals and compares their decoded-frame hashes to the stored hashes. An index mismatch or unavailable ordinal disables that range's action and reports why. Approximate endpoints remain unextractable until refined. Validation is lazy per action, not a startup scan of every saved endpoint, and must not seek or pause the visible player.
- The trusted process stores the movie's display name and last known absolute path as reopening hints. The renderer receives an opaque movie reference and display information, never a persisted path or a reusable source handle. Existing per-window source handles are recreated on each run.
- Choosing another movie preserves the previous movie's locked ranges in its queue. Returning to a movie with a matching fingerprint restores its ranges and order. A copy of the same movie may resolve to the same queue; two movies with different fingerprints keep separate queues. A different fingerprint at a previously used path must not take over the old queue.
- The last active movie is remembered. On entering GIF Extraction after launch, the app attempts to reopen it and restore its queue; when GIF Extraction is the startup workspace, this happens during its startup without blocking the rest of the shell. If the path is unavailable or identity validation fails, the app keeps the saved queue and shows a concise message directing the user to the existing **Open movie** browse control. A movie chosen there is attached to a saved queue only after its fingerprint matches. No new Locate movie button or arbitrary folder search is introduced.
- A future change to the fingerprint algorithm or capture-frame interpretation must use explicit version handling. Older records remain available for recovery, but must not be silently attached to a newly computed, nonmatching identity.

## 3. Saved capture queue

- Store capture records under `path.join(app.getPath('userData'), 'clip-captures')`, separate from `app-settings.json` and the ephemeral thumbnail cache. Keep one bounded, versioned record per movie plus a small last-active-movie pointer; use safe filenames derived from validated movie IDs, never source paths. In development the existing frame caches live under the project folder, and in a packaged app they live beside the executable. Those cache locations are not a suitable durability boundary for user-created captures because an installed executable directory may be unwritable or replaced by an update.
- Persist each **locked** range, including its stable range ID, queue position, exact or approximate endpoint kind, endpoint values, and the source identity needed to validate it. For an exact endpoint, save the canonical frame ordinal and decoded-frame hash, plus review time for presenting the saved range. Do not copy the entire live frame identity into storage. Store `bigint` values as decimal strings in a versioned record. Preserve the next range-ID sequence so a restored session cannot reuse an existing ID. The domain range model owns conversion to and restoration from that validated plain-data representation; it does not own filesystem paths or JSON I/O.
- Save changes asynchronously after each Start or End mark, lock, successful refinement, removal, source switch, and completed publication. Serialize and coalesce writes per movie, replace stored data atomically, and do not hold up player controls, screen changes, or the UI thread for disk I/O. Flush pending writes during orderly shutdown. A save failure leaves the current in-memory work usable but visibly reports that it is not safely saved.
- On restoration, recreate the active review session and its ephemeral source generation, then attach saved ranges as unverified until their exact endpoints are checked against the current index and hydrated with current full frame identities. Approximate timestamp endpoints remain marked as needing exact frames. An invalid or out-of-range capture stays visible with a recovery explanation; it cannot be extracted by accident. Endpoint verification occurs when the user acts on an exact range, as described above.
- Thumbnails are presentation cache, not saved capture data. Recreate them from the source when possible, and show the existing missing-thumbnail state while unavailable. Do not persist Blob URLs or ephemeral thumbnail IDs.
- Persist the one active unfinished Start/End draft with the same compact exact or approximate endpoint representations as locked ranges. Either endpoint may be absent. Restoring an approximate draft preserves its timestamp meaning; it still requires Refine after locking. Check restored exact draft endpoints against the current source before locking. Switching movies saves the draft with its movie and needs no discard prompt.
- Ranges whose media and collection membership were both successfully published need not survive restart in the capture queue. They may remain visible with completed status until the current app session ends. A changed refinement of a completed range becomes a new pending revision while the previously extracted clip remains untouched.
- Failed, cancelled, and interrupted extraction states are not saved across restart. Their locked ranges remain in the unfinished queue and become pending again; the app never automatically extracts them. An in-session failed collection publication retains the existing retry-without-re-encoding behavior. If the app closes or crashes after an MP4 is created but before collection membership is saved, that retry state is not recovered: the range reappears as unfinished and the existing output may remain on disk. Without saved extraction state, the app cannot distinguish this case from an ordinary pending range; an explicit retry may create a second clip. This small feature accepts that crash-window limitation rather than claiming duplicate prevention. A range is removed from the durable unfinished queue only after media creation and collection membership both succeed.

## 4. Extracted clip provenance

- For future MP4 extractions, attempt to embed one small, versioned Clip Sandbox provenance record in the output MP4's movie-level metadata. It records the source display name, source fingerprint and selected stream, and the inclusive **canonical original-source** start and end frame ordinals. Include the saved endpoint identity fields needed to interpret or verify those ordinals if the source is later reopened. Do not embed the private absolute source path, opaque handles, thumbnail data, or transient cache key.
- Own provenance behind a small format-specific read/write contract selected by output clip type. The initial implementation supports the app's MP4 extraction output only. Adding another clip format supplies another implementation; callers do not branch on containers or compose FFmpeg tags. This is a format boundary, not a general plugin system.
- The trusted extraction process derives source identity from the source it actually prepares and encodes, and validates the requested inclusive frame range. It attempts to write provenance while creating the MP4. If metadata alone makes final muxing fail, retry finalization without the custom tag where possible, without re-encoding the video, then verify the media normally. A provenance write or readback failure reports a visible warning but does not fail otherwise successful media extraction and collection publication. The playback and Collection flows accept MP4 clips whose provenance is missing, malformed, or from an older version; provenance lookup returns unavailable rather than blocking the clip.
- The MP4 implementation uses the `mdta` metadata mechanism supported by the project's FFmpeg muxer, with an app-specific, versioned key and a compact payload capped at 4 KiB. The pinned FFmpeg 9.0 build must use `+use_metadata_tags`: a local MP4/FFprobe round trip preserved the custom key with that flag and dropped it without the flag. Namespacing avoids accidental key collisions; it provides no integrity or access protection. An external editor or remuxer may modify or remove metadata, which is accepted for this feature.
- Provenance is stored with the published clip so it remains readable after moving or renaming an intact MP4. The capture store does not become the sole lookup source for published clips. There is no migration or retroactive provenance for existing extracted clips.

## 5. Ownership and trust boundaries

- `GifExtractionSession` remains the application owner of the active movie, capture queue, refinement, and extraction coordination. The domain capture model owns conversion between ranges and validated plain data, as well as range ordering and endpoint invariants. A focused persistent-capture store owns the versioned file schema, JSON encoding, atomic writes, and per-movie retrieval. The UI renders snapshots and recovery actions without writing persistence files directly.
- The Electron main process owns last-known source paths, per-window grants, reopening/relink validation, and durable file I/O. Renderer-facing identifiers remain opaque. Merely listing saved movie queues does not grant filesystem or extraction access; opening a verified movie establishes the active grant.
- The extraction runtime owns format selection, provenance writing and readback, and collision-safe media publication. The collection-publication workflow owns membership commit and in-session retry. The app may request those operations but cannot declare an output fully published based solely on an in-memory callback.
- Parse stored capture JSON and embedded metadata at their boundaries with schema, type, range, length, and version checks. Unknown or damaged capture records should be reported and preserved for recovery, rather than silently discarded or executed as instructions. Missing or invalid clip provenance must be tolerated. Keep persisted paths out of clip metadata and renderer IPC.

## 6. User-visible acceptance

1. Lock two ranges in movie A, switch to movie B and lock one there, then return to A: A's two ranges reappear in their original order and B keeps its own range. No locked range is discarded on the switch.
   An unfinished exact or approximate draft in A also returns, including after restart; switching needs no discard confirmation.
2. Restart with GIF Extraction as the startup workspace: the last movie and its unextracted ranges reappear after source validation. Starting on another workspace restores them upon entering GIF Extraction. The ranges also remain available when switching between GIF Extraction and Refine.
3. If the movie moved or changed, the saved queue remains visible with extraction disabled and a message points to the existing Open movie control. Opening the original movie and verifying its fingerprint restores actionable ranges; selecting different content never attaches the old queue.
4. Exact and approximate ranges restore with the same endpoint meaning. Exact ranges validate saved frame identity on demand before Refine or Extract; opening the app does not validate every endpoint or disturb playback. Missing thumbnails do not remove ranges or enable an unsafe action.
5. After its queue update has saved successfully, a fully published range is absent from the unfinished queue on the next restart. Failed or cancelled extraction status is not retained. An in-session collection-save failure can still retry publication without re-encoding; after restart, the user may need to inspect the destination before retrying the unfinished range.
6. A newly published MP4 normally contains readable source identity and inclusive canonical start/end frames. The read-back values match the actual extraction request, and renaming or moving an untouched MP4 does not lose that record. If metadata cannot be written, the clip still publishes and a warning is shown. Clips with missing or invalid provenance still load and play normally.
7. A failed capture-store write or invalid saved record produces a visible, actionable error; it is not reported as safely saved. Existing unrelated movie queues are preserved.

Verification must cover persistence round trips and corruption handling, asynchronous save behavior, source reattachment and lazy stale-frame rejection, MP4 metadata readback with the bundled FFmpeg/FFprobe (including the missing-tag case), and the actual Electron movie-switch/restart workflows. Test the user-visible result, not only serialized JSON or mocked calls.

## 7. Scope limits and decisions recorded

- The separate screen/panel-preference handoff is not part of this feature or its execution plan. GIF Extraction and Refine keep their current shared capture panel while this feature is implemented.
- Locked captures and the one active unfinished Start/End draft are durable; player position, selected range, and thumbnail cache remain session state.
- Clip provenance is attempted for future MP4 extractions; absence is nonfatal. Existing clips and other output formats do not gain provenance in this feature.
- Provenance need not survive an external edit or remux. The app must still validate metadata it reads rather than treating it as proof that a source file is unchanged.
- No automatic extraction, full-disk source search, external sync, or general media catalog is introduced.
