# Preview exact captures and revise GIF shortcuts

Status: Original feature spec signed off on 2026-09-28. Revised A–B loop spec and execution plan signed off by the user on 2026-10-03. On 2026-10-03 the user accepted the measured boundary misses provisionally and authorized completing the app with A–B looping, followed by manual review on real clips. That review is a final milestone; if the user does not sign off, replace the loop mechanism while keeping the GIF controls and capture rules. The GIF controls are implemented and under verification; the user has not yet given the final real-clip verdict.

## 1. User goal

While capturing or refining a clip, the user can inspect its exact Start and End frames and watch their range as a normal-speed review loop before locking it. The loop is an aid for short adjust-and-watch iterations. Boundary behavior is accepted from measured pictures in the running app, not guaranteed by the playback mechanism. Space stops the loop on an exact frame ready for scrubbing. The same keyboard layout works in GIF Extraction and Refine Gif. Silence is preferred only when it is straightforward; audible preview is acceptable.

## 2. Controls and range context

| Key | Action |
| --- | --- |
| `Q` | Mark or replace Start from the displayed frame, as today. |
| `W` | Mark or replace End from the displayed frame, as today. |
| `A` | Jump to the exact Start frame. If playback or loop preview is running, stop it and enter frame scrub; a stopped loop remains resumable from Start. |
| `S` | Jump to the exact End frame under the same rule; a stopped loop remains resumable from End. |
| `Z` | From exact scrub, start a normal-speed proxy loop for the exact Start–End frame selection; while that loop runs, restart it at Start. The player loops by time, so boundary pictures are measured rather than guaranteed. |
| `Space` | While the loop plays, stop on an exact in-range frame in scrub mode. While that same range is paused for scrub, resume its loop from the exact frame now displayed. Otherwise retain ordinary play/pause behavior. |
| `X` | Lock an unlocked draft in GIF Extraction or commit staged endpoints in Refine Gif. It is disabled for a selected locked range. If an eligible loop runs, stop it first. |
| `E` | Retain the existing extract-current action; unavailable while a loop runs. |
| Left / Right | Retain exact adjacent-frame stepping. |

Matching visible buttons, keycaps, disabled states, and shortcut help must use the new mapping. The actions must also be available by pointer so a user need not know the keys; the shared play/pause button follows the same loop pause/resume behavior as Space. No shortcut fires while typing into an editable control or when its screen is inactive.

The preview target is the current unlocked draft when it has two endpoints. A selected locked range in the Clips panel can also be previewed. Starting a new draft with `Q` makes that draft the target; `W` can complete that draft, making `X` relevant again. This does not unlock or edit the previously locked range. Choosing a locked card makes that card the preview target, with `X` disabled. On entering Refine Gif, Start and End are copied from the locked range into a temporary edit. As today, `Q`/`W` first focus an endpoint when needed and then replace it with the displayed exact frame. `A`/`S` and `Z` inspect the temporary pair without changing it. `X` writes a valid revised pair back to the same locked range; Back discards the temporary edit. An earlier saved clip is never changed by preview or refinement. The UI identifies the active target and shows why Jump, Loop, or Lock is unavailable.

Jump and loop require **both** endpoints to be exact frames from the current source generation. `Z` is available in exact scrub with a current exact range and during that range's running loop; it is disabled during ordinary full-movie playback. `A`/`S` may still stop ordinary playback and jump into exact scrub. Jump allows equal endpoints; Loop Preview requires Start before End and is disabled for a one-frame range. A one-frame capture remains valid to lock and extract. Timestamp marks made during ordinary playback remain valid for the existing lock-and-refine path, but are not silently rounded to frames for Jump or Loop. `X` continues to permit those inexact captures under the existing rules.

From exact scrub, `Z` starts preview at Start; during a running loop it restarts at Start. It is disabled during ordinary full-movie playback. A changed target, revised endpoint, removed range, replaced movie, screen change, or session disposal ends a running or paused loop. `Q`/`W` remain available during ordinary full-movie playback, as today. During a running loop, they cannot mark from a sampled playback clock; the user presses `Space` before revising an endpoint. In paused exact scrub, Q/W can mark the displayed frame when that mark is valid for the current draft or staged Refine pair; on a selected locked range, Q begins a new draft and W can then mark its End. A changed endpoint or target cancels the resumable loop: Space returns to ordinary play/pause and Z starts a new loop for the revised exact range. A/S during a running loop stop the loop and scrub to Start or End; Space resumes the unchanged loop from that exact displayed endpoint. A/S jumps and arrow steps while paused remain in exact scrub; if the resulting displayed frame is still within the unchanged range, Space resumes the paused loop from it. Seeking or stepping outside the range ends the paused loop. The next Space starts ordinary playback from the exact frame now displayed, with A–B disarmed. For an unlocked draft or staged Refine pair, X during a running loop safely stops and disarms it, then locks or commits that same pair; it leaves exact scrub available and clears resumable-loop state. X is disabled when a selected locked range is the target, whether its loop is running or paused. The X command captures its source, target identity, and endpoint revision before awaiting stop or player recovery and rechecks all three after every awaited step, including saved-draft preparation, and immediately before Lock/Commit. If the target changed, it skips Lock/Commit and reports that the action was cancelled; if recovery fails but the target is unchanged, it still completes Lock/Commit and keeps ordinary playback disabled. E and its pointer control are disabled while a loop runs, and no extraction is queued by that key press. Locking does not save media or start extraction. Live endpoint editing while a loop runs is a possible future feature; this version requires stopping first because the existing marking interaction cannot supply exact frame identity from clocked playback.

## 3. Proposed A–B proxy loop

### Proxy timeline and player behavior

The range is selected by exact frame ordinals, but this playback mechanism is **timestamp-driven**. The host converts Start and End ordinals to integer proxy presentation-time ticks, maps those ticks to LibVLC player microseconds, then LibVLC seeks and loops using its A–B time controls. The player does not advance through a list of known frame ordinals or receive an instruction to wrap after painting End. Exact A/S jumps and source extraction remain frame-based. Recorded boundary misses and outside pictures are provisionally accepted for real-clip review; they are not described as exact loop behavior.

Use the already open prepared GOP1 review proxy for loop playback. Start's indexed **proxy** PTS identifies the intended A picture; the provisional player call may place A one microsecond earlier for nonzero Start to make that picture visible at wraps. B is chosen strictly inside End's proxy PTS interval, between End's PTS and the following frame's PTS. Convert A and B to LibVLC player microseconds before passing them to the player. Use the proxy timeline, never original-source time or nominal frame rate. Capture endpoints are canonical frame ordinals; the prepared frame map declares ordinal identity between source and proxy, so no source-timestamp-to-proxy-timestamp map is needed. Preparation currently checks matching frame counts, which alone does not prove picture-by-picture alignment; coded-picture fixtures, including a source that actually enters timestamp normalization, must verify that selected original, canonical, proxy, and extracted ordinals identify the same pictures. After encoding and indexing the final proxy, preparation records an optional ordinal-to-proxy-PTS timeline alongside the prepared cache; doing so during encoding could miss timestamp changes made by the muxer. A missing or invalid loop timeline may be regenerated from the cached proxy index and does not invalidate proxy playback or exact scrub. The host looks up Start, End, and following-frame PTS from that timeline without decoding the movie again, checks ordering and representability after conversion, and validates the live review session and ordinal pair. The app separately invalidates a preview request when its selected draft, locked range, or staged pair changes while that request is pending; cleanup of an old request cannot stop a newer preview. The development probe establishes a deterministic proxy-metadata-to-LibVLC-clock rule, including origin offset and drift, with varied first PTS and CFR/VFR/normalized fixtures. For each later proxy, the host derives its mapping from that proxy's indexed metadata using the verified rule before enabling Z; if no general rule can be established, the A–B mechanism stops for discussion. The probe checks the resulting mapping before A/B or Space lookup use it. After Space samples LibVLC player time, compare that sample with converted proxy-frame times to find its ordinal. For End at the proxy's final frame, use a trustworthy indexed duration if available; otherwise use the preceding positive proxy-frame gap as an explicitly approximate hold interval.

No B placement proves that End will be shown or End+1 suppressed: LibVLC A–B uses a clock deadline and seek, and scheduling/display can race the boundary. The probe tunes a fractional offset within End's interval and records the two margins. Choose B in integer proxy PTS ticks, convert with rational timebase arithmetic to integer LibVLC player microseconds, and recheck that B is strictly between End and End+1 in both domains and after Start in player time. If conversion collapses an interior margin, reject loop preview for that pair with a clear reason. The measured result, including boundary misses, decides whether this mechanism is acceptable.

To start preview from exact scrub, the development probe compares seek-then-arm with arm-then-seek using converted player-time A/B. The provisional build uses arm-then-seek with a one-microsecond A preroll for nonzero Start because that painted Start at observed wraps; record remaining boundary misses and use the same order for Z and resume at normal 1× rate. The first painted picture after a seek is **not** assumed to be Start. The pinned setter changes both A and B and may seek if current time is outside the pair. This version stops preview before endpoint edits. On the first Space, pause playback, sample its player time, select an exact canonical frame inside the range through the converted proxy timeline, reset A–B so no loop remains armed during scrub, and display that exact frame. If reset reports failure, ordinary playback must not continue with a possibly armed loop: recover by reopening the same proxy in a fresh player paused at the exact frame selected by Space, or disable ordinary playback with an error while retaining exact scrub and capture marks if recovery fails. Retain only the unchanged range as a resumable preview after successful reset. On the next Space, convert the currently displayed exact frame ordinal's proxy PTS to player time, apply the probe-selected seek/arm order from that frame, and play; `Z` instead restarts at Start. Measure the first resumed picture and revision latency. Muting is optional: use it only if the pinned player supports it reliably without complicating loop setup or recovery. If preview changes the audio setting, restore its prior value on every exit path; otherwise retain the player's ordinary audio behavior. The UI makes no silence promise. Extracted clips retain their source audio behavior.

The pinned source checkout is sparse and normally contains only `include`. Inspect source with `git -C tools/frame-review/.deps/vlc-source show HEAD:src/player/player.c` and `HEAD:src/player/input.c`. Cite the pinned VideoLAN [player loop scheduler](https://code.videolan.org/videolan/vlc/-/blob/baad2c523c1934470bb351105efc352e0678dd55/src/player/player.c), [seek handler](https://code.videolan.org/videolan/vlc/-/blob/baad2c523c1934470bb351105efc352e0678dd55/src/player/input.c), [LibVLC wrapper](https://code.videolan.org/videolan/vlc/-/blob/baad2c523c1934470bb351105efc352e0678dd55/lib/media_player.c), and [audio-only A–B test](https://code.videolan.org/videolan/vlc/-/blob/baad2c523c1934470bb351105efc352e0678dd55/test/src/player/abloop.c), rather than claiming those are present as working-tree files. The checked-out [header](../../tools/frame-review/.deps/vlc-source/include/vlc/libvlc_media_player.h) declares the time and mute APIs.

### Picture oracle and acceptance gate

Use CFR and proxy-preserved VFR fixtures with a machine-readable ordinal tile in each picture. Instrument each actual canvas paint with the decoded tile and monotonic time; native callback delivery alone is insufficient. Also record per-cycle `droppedBeforeWrite` changes, write-to-acknowledgement delay, player timer points, A/B settings, seek events, and frame/source generations so native/renderer losses are distinguished from A–B behavior. Cover several-second ranges, Start=0, End at the final proxy picture, and short frame intervals. First run three cycles for each representative and boundary case at a central B offset. If that offset misses a boundary, paints End+1, or misses a seam/speed limit plausibly affected by B placement, compare at most one earlier and one later offset in three-cycle diagnostics and repeat the chosen candidate gate. The gate is 30 normal-load cycles on each of one CFR and one VFR several-second range, plus 10 loaded cycles on one representative range; boundary cases need three cycles each. Stop early and diagnose an observed normal-load failure instead of completing the matrix. Report counts with denominators, Start/End presence, any outside ordinal, End dwell, seam, 1× timing, and B margins. Keep per-paint traces in a local artifact and send only compact summaries and anomaly excerpts for review. Longer soak runs are optional follow-up to a concrete anomaly or a separately agreed confidence target, not a prerequisite for this feature.

Continue implementation with the observed A–B picture-boundary behavior recorded as a provisional limitation. The coded-picture probe must still report every Start/End miss, outside ordinal, End dwell, and black flash; do not convert an observed failure into a passing measurement or claim exact loop boundaries. A new or materially worse picture anomaly triggers focused diagnosis. Each normal-load wrap should show at most 150 ms of extra End-to-Start delay beyond End's indexed proxy-frame interval (or its stated estimate for the final-frame diagnostic). On the several-second core ranges whose End+1 PTS is indexed, every Start-to-Start wall interval must be within 5% of the converted indexed inclusive cycle duration and the median absolute deviation within 3%. Final-frame diagnostics report timing without applying that strict percentage gate when End's hold is estimated. Under normal load, Z-to-first-Start, Space-to-exact-scrub, Space-resume-to-first-picture, and Z-after-Q/W-to-new-Start must each take at most 500 ms from the accepted key event to canvas paint; the last measurement excludes the user's marking time. Inspect the actual app for black flashes that ordinal tiles alone cannot reveal. Judge artificial-load misses by reachability and visible consequence. Record tested source durations, frame intervals, cycle counts, timing limits, and results. A one-frame range is not a loop acceptance test. Final acceptability of the boundary behavior belongs to the user's manual real-clip review after delivery.

On the first Space, sample the LibVLC player timer near the pause, find the greatest canonical ordinal whose converted proxy PTS is at or before that player time, and restrict the result to `[Start, End]`: if the timer maps before Start, show Start; if it maps after End, show End. This keeps scrub inside the selected range even near an A–B wrap. The chosen ordinal is exact, but the timer sample is not the painted picture's exact identity. Target a result within one ordinal of the picture visible when Space was pressed under normal load and measure that error with the tile oracle, including near wraps. Do not promise the one-frame bound in production unless the probe supports it; if it fails, revise the handoff or bring the tradeoff back for review. The next Space resumes the same loop from the currently displayed exact ordinal if that ordinal remains within the unchanged range; test its first painted picture as well. Never use loop time as a new capture endpoint.

### Fallback and failure handling

If the user does not sign off after manually trying A–B preview on real clips, discuss a renderer-driven exact-frame loop before implementing it. That option batch-decodes selected proxy frames, bounds memory, schedules presentation by indexed intervals, and reuses frames across small revisions. It needs a batch decode path, memory on the order of hundreds of megabytes for several seconds of raw RGBA at preview resolution, synchronization, and a new render owner. Only the loop mechanism should change in that follow-up; the controls, exact jumps, capture rules, and original-source extraction remain the feature contract. The fallback is not authorized for this implementation.

Preview remains session-local. Failed arming, seeking, muting, or resetting preserves marked endpoints and the queue, reports a recoverable error, and leaves exact scrub available. Source/target revisions, screen departure, and disposal clear the native loop or isolate a player that could not clear it, and restore preview audio state if preview changed it. Stale callbacks and completions cannot restart an obsolete loop or overwrite exact scrub.

## 4. Ownership and UI boundaries

- `RangeCaptureModel` and `RefineGifSession` continue to own draft/locked and staged endpoint rules. The capture queue and extraction status do not change because of preview.
- `GifExtractionSession` chooses the current draft or selected locked range and coordinates preview lifetime with capture/refinement changes. The trusted frame-review boundary owns proxy-time lookup, A/B validation, optional audio-state restoration, and native playback; raw media/cache paths stay behind that boundary.
- `FrameReviewPlayerControl` owns displayed-frame identity, transport state, and exact-scrub transition. GIF Extraction and Refine Gif use the same physical player and keyboard controller.
- Both screens present Jump Start, Jump End, Loop Preview, and Lock/Commit controls with the revised keycaps. Neither labels the loop as silent. The Refine screen continues to stage edits until `X`; Back discards uncommitted edits.

Refine Gif remains a separate contextual screen. It can take a range marked approximately during playback, seek near each timestamp, and let the user replace it with an exact displayed frame. It also keeps revisions to a locked range reversible until `X` and provides Next inexact range. The new GIF Extraction controls preview a selected locked range but do not make `Q`/`W` edit that locked range in place; `Q` still begins a new draft there. Removing Refine would require moving its approximate-to-exact and reversible-edit behavior into GIF Extraction, which is outside this feature.

This feature does not change original-source extraction, output naming, collection publication, or the separate future flow for editing a saved clip without its source movie.

## 5. Acceptance behavior and required evidence

1. In GIF Extraction, an exact unlocked draft and a selected exact locked range each allow `A`/`S` jumps and `Z` preview. Refine Gif allows the same actions on its staged exact pair without committing it.
2. Jumping with `A`/`S` while a loop plays stops it and displays the chosen canonical endpoint in scrub mode; `Space` resumes that unchanged loop from the endpoint. The first `Space` during a loop stops on an exact in-range frame and leaves arrow stepping usable. A second `Space` resumes the same unchanged loop from the displayed in-range exact frame; `Z` restarts at Start. If scrub leaves the range, Space begins ordinary playback from the exact frame then displayed, with A–B disarmed.
3. The measured Electron probe reports all boundary misses and outside pictures, including the provisionally accepted A–B behavior, without claiming exact loop boundaries. The seam and several-second core-range 1× timing limits above remain checks; final-frame diagnostics report timing without that percentage gate when End's hold is estimated. Preview may be audible; it does not leave ordinary playback muted or alter extracted audio. One-frame ranges cannot loop but remain valid to lock and extract. Loaded miss/leak rates are reported separately. The user makes the final acceptability decision by manually trying the delivered app on real clips.
4. Timestamp or mixed endpoints cannot jump or start a loop. Their existing lock, Refine, and extraction eligibility rules remain intact.
5. Changing targets, leaving a screen, replacing a source, removing a range, or shutting down clears A–B and restores audio only if preview changed it, without reviving stale preview. `Q`/`W` during loop preview do not capture a sampled playback timestamp. A failed preview leaves capture intent intact and permits exact scrub recovery. Space returns an exact in-range ordinal; its difference from the last painted picture is measured and reported rather than assumed.
6. The visible controls, keyboard help, and keyboard behavior agree on `Q/W`, `A/S`, `Z`, `X`, `Space`, `E`, and Left/Right in both GIF screens, including X stopping an eligible loop before Lock/Commit, X disabled for a selected locked range, and E disabled while a loop runs. Pointer and keyboard paths produce the same user-visible result.
