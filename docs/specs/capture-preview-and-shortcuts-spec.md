# Preview exact captures and revise GIF shortcuts

Status: Signed off by the user on 2026-09-28; silent-loop and media-proof revisions under review on 2026-09-29. Implementation awaits execution-plan sign-off.

## 1. User goal

While capturing or refining a clip, the user can inspect its exact Start and End frames and preview the inclusive range as a silent, normal-speed loop before locking it. Space stops the preview on an exact frame, ready for further frame scrubbing. The same keyboard layout works in GIF Extraction and Refine Gif.

## 2. Controls and range context

| Key | Action |
| --- | --- |
| `Q` | Mark or replace Start from the displayed frame, as today. |
| `W` | Mark or replace End from the displayed frame, as today. |
| `A` | Jump to the exact Start frame. If playback or loop preview is running, stop it and enter frame scrub. |
| `S` | Jump to the exact End frame under the same rule. |
| `Z` | Start the silent exact Start–End loop from Start at normal 1× speed. |
| `Space` | During loop preview, stop it and leave the displayed position in exact frame scrub. Outside loop preview, retain the existing play/pause behavior. |
| `X` | Lock the draft range in GIF Extraction or commit staged endpoints in Refine Gif. |
| `E` | Retain the existing extract-current action. |
| Left / Right | Retain exact adjacent-frame stepping. |

Matching visible buttons, keycaps, disabled states, and shortcut help must use the new mapping. The actions must also be available by pointer so a user need not know the keys. No shortcut fires while typing into an editable control or when its screen is inactive.

The preview target is the current unlocked draft when it has two endpoints. A selected locked range in the Clips panel can also be previewed. Starting a new draft with `Q` makes that draft the target; choosing a locked card makes that card the target. On entering Refine Gif, Start and End are copied from the locked range into a temporary edit. As today, `Q`/`W` first focus an endpoint when needed and then replace it with the displayed exact frame. `A`/`S` and `Z` inspect the temporary pair without changing it. `X` writes a valid revised pair back to the same locked range; Back discards the temporary edit. An earlier saved clip is never changed by preview or refinement. The UI identifies the active target and shows why Jump or Loop is unavailable.

Jump and loop require **both** endpoints to be exact frames from the current source generation. Jump allows equal endpoints; Loop Preview requires Start before End and is disabled for a one-frame range. A one-frame capture remains valid to lock and extract. Timestamp marks made during ordinary playback remain valid for the existing lock-and-refine path, but are not silently rounded to frames for Jump or Loop. `X` continues to permit those inexact captures under the existing rules.

`Z` starts or restarts preview at Start. A changed endpoint, removed range, replaced movie, screen change, or session disposal stops an active preview before using any new target. `Q`/`W` remain available during ordinary full-movie playback, as today. During loop preview, they do not mark from the temporary asset's relative playback clock; the user presses `Space` to enter exact scrub before changing an endpoint. Jumping, stepping, or seeking away also exits loop preview. Locking does not save media or start extraction.

## 3. Proposed exact proxy loop solution

### Prepared asset and identity

Use the existing prepared GOP1 review proxy as the input for preview. Preparation validates that proxy picture ordinal `N` corresponds to canonical source frame ordinal `N`; the canonical frame index remains the identity used for captures and eventual extraction from the original movie. The proxy's own indexed presentation timeline governs preview timing. Preview must not use the original movie, a nominal frame rate, or a rounded playback timestamp to decide which video pictures belong to the loop. Proxy creation rebases and repairs timestamps and Matroska quantizes them, so picture identity matches the source while presentation intervals need not be bit-for-bit identical. If End is the proxy's final frame and it has no trustworthy explicit duration, use the positive gap from the preceding proxy frame as its hold duration; this rare boundary is an approximation, not an exact-duration requirement.

The preview request is an immutable pair of exact canonical ordinals plus source generation. The trusted process selects proxy frames from Start through End **by ordinal, inclusively**, and produces a temporary Matroska video-only range asset. It preserves the selected frames' relative presentation intervals and rebases playback time to zero. The asset contains no audio stream. Before playback, production checks its packet count, every selected packet's payload hash and timestamp, its single video stream, and the codec configuration against the validated proxy index; it does not decode every generated asset. The probe and fixtures decode the whole asset to establish that these checks imply the requested ordered picture sequence for this proxy profile. If a seam treatment appends another picture, it may only repeat a picture already in the selected range and must be verified separately. A changed endpoint invalidates that asset. Preview generation may begin as soon as both exact endpoints exist; it must not block further marking or scrubbing, and `Z` shows a clear preparing state until the current asset is ready.

Play the verified asset through the existing LibVLC player silently at normal 1× speed and repeat that bounded asset. Show a visible “Preview is silent” cue while it plays. Since it contains no outside-range video picture, a late loop boundary cannot reveal a frame outside the requested range. This still needs a real playback proof that Start and End are actually shown at the wrap, that the repeat is usable at 1×, and that preview preparation is responsive enough for capture work. Stopping preview returns to the prepared full-movie review session and resolves the current preview position to an exact frame within the selected range for frame scrub. Ordinary movie playback keeps its existing audio behavior when resumed; extracted clips retain their original-source audio. Jump-to-Start and Jump-to-End use canonical ordinals directly, without going through the temporary asset.

### Why the time-based A–B loop is not the proposed solution

The pinned LibVLC 4 A–B API takes times, not frame identities. Its pinned implementation schedules a wall-clock deadline and seeks back at that deadline; its own A–B test exercises an audio track without a video track. Together with Clip Sandbox's sampled playback-time callback, this gives no basis for claiming that the End picture is displayed before the wrap. The execution plan does not need an A–B comparison and must not make that API the correctness foundation or treat a successful time-boundary check as proof of an exact-frame loop.

The execution plan must detail how to construct the video-only range asset. Prototype an input seek to Start's indexed proxy timestamp followed by stream copy of exactly End minus Start plus one video packets into Matroska. The prepared proxy is GOP1 MPEG4 with B-frames disabled, so a packet slice may avoid another video encode. Exclude the proxy audio stream. Establish packet-to-picture correspondence for the pinned proxy profile on decoded fixtures, including a noninitial range. In production, build the packet index without another full proxy decode; require its packet count to equal the existing decoded proxy frame count, all packets to be keyed and usable with monotonic PTS, and each output packet's payload hash and codec configuration to match the validated proxy. A timestamp seek alone is not an ordinal proof. Check the actual proxy time base and output timestamps rather than assuming exact millisecond conversion or a zero origin. Preserve relative VFR intervals if the proxy has them. Measure the extra indexing work and a range far into a representative movie; ordinary playback and exact-frame readiness should not wait for an avoidable whole-proxy hash pass. Keep complete decoded-picture comparison in the probe and fixtures, not the per-revision production path. Test repeat playback of the plain slice first, then test a copy of Start as an in-file successor to End if the real player shortens End or shows a visible seam. Do not commit either seam treatment without measuring its displayed-frame sequence and timing. If packet copy cannot meet decoded-picture, timing, or playback requirements, compare a measured ordinal-trim/re-encode fallback under the same oracle. Measure generation latency after initial marks and revisions, repeated playback timing, silent-preview presentation, and cleanup on endpoint replacement. If no temporary-asset approach meets the user-visible accuracy or responsiveness checks, record the result and bring a revised solution for review rather than silently relaxing the exact-frame requirement.

Research basis: the [pinned LibVLC 4 API](https://videolan.videolan.me/vlc/master/group__libvlc__media__player.html) exposes a time-based A–B loop; its pinned source at `tools/frame-review/.deps/vlc-source` (`src/player/player.c`, `test/src/player/abloop.c`) provides the deadline/seek behavior above. The [FFmpeg command reference](https://ffmpeg.org/ffmpeg.html) documents stream-copy seeking and frame-count limits; the [FFmpeg formats reference](https://ffmpeg.org/ffmpeg-formats.html) documents packet hashes and concat duration directives. The [Matroska element specification](https://www.matroska.org/technical/elements.html) allows a BlockDuration, but its presence and accuracy in our proxy must be checked rather than assumed. These are implementation options to prove, not evidence that the resulting preview already works.

### Exact validation oracle

Use prepared CFR and, if the production proxy preserves nonuniform intervals, VFR fixtures whose successive pictures carry independently readable frame numbers. For representative several-second ranges, first decode the generated plain range asset and verify its complete picture sequence equals the requested inclusive ordinal slice; separately identify and verify any appended seam picture. Then, in the real Electron player, record picture codes at the native frame-delivery boundary and inspect the pictures actually presented by the canvas across at least three complete loops. In each observed cycle, Start and End must appear, no presented picture may lie outside the range, and the wrap must return to Start. Measure End's visible dwell and the Start-to-Start period against the indexed intervals, allowing documented scheduling tolerance; an extra Start picture must not produce a perceptible pause or break usable 1× motion. Record the delay from an endpoint change to a ready preview. Exercise `Space`, `A`, and `S` during preview and verify that each leaves a valid exact scrub frame. A filename, A/B setting, sampled playback clock, play-state flag, or final screenshot is insufficient evidence.

### Playback state and failure handling

Preview is session-local, never persisted with a captured range. Starting a newer preview invalidates pending displays, transport operations, and temporary assets from the prior preview. On `Space`, resolve the current preview position to an exact canonical frame inside the range and show it in scrub mode; the returned frame need not be the same picture that was last sampled during clocked playback. If generation or playback fails, stop preview, retain the marked endpoints and queue, show a recoverable error, and leave ordinary exact scrubbing available. Stale completions after a mark, source, screen, or session change cannot restart playback or publish an obsolete asset.

## 4. Ownership and UI boundaries

- `RangeCaptureModel` and `RefineGifSession` continue to own draft/locked and staged endpoint rules. The capture queue and extraction status do not change because of preview.
- `GifExtractionSession` chooses the current draft or selected locked range and coordinates preview lifetime with capture/refinement changes. The trusted frame-review boundary owns proxy-frame selection, temporary preview assets, and bounded native playback; raw media/cache paths stay behind that boundary.
- `FrameReviewPlayerControl` owns displayed-frame identity, transport state, and exact-scrub transition. GIF Extraction and Refine Gif use the same physical player and keyboard controller.
- Both screens present Jump Start, Jump End, Loop Preview, and Lock/Commit controls with the revised keycaps. While the loop plays, both show that the preview is silent. The Refine screen continues to stage edits until `X`; Back discards uncommitted edits.

Refine Gif remains a separate contextual screen. It can take a range marked approximately during playback, seek near each timestamp, and let the user replace it with an exact displayed frame. It also keeps revisions to a locked range reversible until `X` and provides Next inexact range. The new GIF Extraction controls preview a selected locked range but do not make `Q`/`W` edit that locked range in place; `Q` still begins a new draft there. Removing Refine would require moving its approximate-to-exact and reversible-edit behavior into GIF Extraction, which is outside this feature.

This feature does not change original-source extraction, output naming, collection publication, or the separate future flow for editing a saved clip without its source movie.

## 5. Acceptance behavior and required evidence

1. In GIF Extraction, an exact unlocked draft and a selected exact locked range each allow `A`/`S` jumps and `Z` preview. Refine Gif allows the same actions on its staged exact pair without committing it.
2. Jumping while a movie plays stops playback and displays the chosen canonical frame in scrub mode. `Space` stops a running loop on an exact displayed frame and leaves arrow stepping usable.
3. Preview of a range with Start before End plays silently at normal 1× speed, starts on Start, includes End, wraps to Start, and displays no picture outside the selected ordinal range. The UI indicates that preview is silent. Verify this in the real Electron app over multiple cycles of a representative several-second range with coded CFR and, if the proxy preserves variable intervals, VFR fixtures. The temporary asset has no audio stream; ordinary movie playback remains audible when resumed, and extracted clips retain their existing audio behavior. One-frame ranges cannot start Loop Preview but remain valid for capture and extraction.
4. Timestamp or mixed endpoints cannot jump or start a loop. Their existing lock, Refine, and extraction eligibility rules remain intact.
5. Changing marks or selection, leaving a screen, replacing a source, removing a range, or shutting down clears active loop playback and cannot revive a stale preview. `Q`/`W` during loop preview do not capture a relative timestamp from the temporary asset. A failed preview leaves capture intent intact and permits exact scrub recovery.
6. The visible controls, keyboard help, and keyboard behavior agree on `Q/W`, `A/S`, `Z`, `X`, `Space`, `E`, and Left/Right in both GIF screens. Pointer and keyboard paths produce the same user-visible result.
